## 一、总体结论

1. **同步架构核心正确性已在前两轮收敛**：LWW+version 平局裁决确定性收敛、墓碑时间戳裁决、复活裁决防重复行、白名单双向校验（读侧 db_loader + 写侧 merge）、push 先 meta 后 data 顺序、原子落盘、空数据覆盖守卫、KeyMismatch 守卫矩阵——全部在位且有测试。
2. **本轮发现的最大缺陷是「S7 空列表防御反向锁死首台设备附件上传」**：09-13 批 B 加入的防御未区分「列表探测异常」与「云端真的没有附件」两种状态，首台设备从零同步时每轮被误判为前者，附件永久无法上传（其他设备永远拉不到）。这是**前次修复引入的回归**——防御性代码必须区分"异常态"与"初始态"，本次以存在性探测三分叉修正。
3. **S31 的 GC↔pull 对打架循环确认成立且已修复**：pull 差集只看「云端有-本地无」不看本地引用，GC 删除无引用附件后云端孤儿每轮被拉回、插占位行、再被 GC 删，无限循环。修复为差集增补活跃引用过滤，孤儿留云端不下载。
4. **性能**：push 空库守卫原先每轮做全表加载→len()→再 COUNT 复核→第三次加载，万行级模块每轮多两次全量扫描+一次全量物化；改 COUNT 后非空库仅索引扫描即过。
5. **遗留但评估为「合理推迟」的项**（S15 流式/S16 墓碑 GC/S14 push_only 先 pull/S18 行级 LWW 字段盲覆盖/S25 v2 盐强度/S26 密码 zeroize）：维持 09-13 的推迟决策，理由复核后依然成立（触发规模未到/需产品拍板/跨端密钥链路联动单独立项），详见 §四。S29 dir_cache 失效已由收尾批次 F8 收口，不在遗留清单。（2026-09-14 勘误补充：S4 的超时半项已于当日后续批次改 read 语义收口，见 §四行内更新与 F10；**同日第三批 F11-F13 将 S4 全量收口**——确定性 nonce + S3 原生 multipart + WebDAV 自造分片，S4 移出遗留清单）
