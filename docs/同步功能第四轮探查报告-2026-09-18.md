## 一、总体结论

1. **本轮最大缺陷是「push 组装清单时用本地重建索引整体替换远端索引」**（F14）：与 push.rs 模块文档第 12-16 行宣称的「新清单 = 远端清单拷贝 + 本地有数据的桶覆盖」直接矛盾——实现从未按该口径写。他端同轮已上传并登记的桶条目被清单孤立（对象在云端、引用消失），本端及他端 pull 均看不见这批数据，属**多设备并发下的静默数据丢失**。已修为桶级合并。
2. **第二个 P0 是 rekey 后的「指纹密钥无关」空洞**（F15）：桶指纹是对明文行的 canonical 哈希，换密钥后指纹不变 → 增量比对把所有桶判为「未变」全部跳过，云端整体停留旧 Key 密文，新设备永远 KeyMismatch。已新增 `push_all_force_full` 强制全量重传路径并接入 rekey。
3. **冲突/失败传播闭环存在两个洞**：pull 有表合并失败仍把 `manifest_epoch` 推进到新值，下轮在 epoch 判等早退，失败表**永不重试**（F16）；merge 表级失败吞错返回 Ok 且事务照常提交，留下文档明令禁止的「数据已合并、删除未应用」半合并态，且账本为不完整表记新指纹（F17）。两者叠加即成永久静默空洞，已分别以 epoch 回退 + 回滚抛错收口。
4. **重试矩阵有两个盲区**：push_only（「修改后立即同步」入口）与 rekey 全量重传均为裸调用，无业务级退避重试——瞬断直接失败（F18/F15 联动收口）。
5. **协议合规、断点续传、加密体系复核无回归**：S3 SigV4/multipart/分页、WebDAV MKCOL/PROPFIND/409 自愈、确定性 nonce 分片续传（F11-F13 前轮）逻辑在位且有测试；本轮仅发现错误处理路径自身的一处多字节 panic（F21）。
6. **性能与安全维度未发现需本轮修复的新问题**；两处密码学强度项（nonce 截断宽度、AAD 绑定）评估为需变更密文格式的独立立项，见 §四。

## 三、六维评估（对齐探查任务 1-6）

1. **协议完整性与合规性**：S3 — SigV4 签名（UNSIGNED-PAYLOAD）、region/service 段推导（含 OSS）、multipart Create/UploadPart/Complete/Abort、ListObjectsV2 分页 >1000、条件写 `If-Match`/`If-None-Match: *`。WebDAV — MKCOL 逐级建链、PROPFIND Depth:1 + resourcetype 目录识别、409 自愈重建（前轮 F8）、Basic auth。两协议清单 CAS 均有「服务端忽略条件头」的回读校验兜底。合规。已知窄缺口见 §四 N9/N10/N11。
2. **上传/下载/删除/更新稳定性（网络环境）**：三层重试矩阵齐备——HTTP 层 100/200/400ms（限流/认证类不重试）、业务层 2/4/8s 普通 + 30/60/120s 限流退避、认证错误首错即返（S6）；`read_timeout` 只断停滞不断慢速（F10）。本轮补齐 push_only 与 rekey 两个裸调用盲区（F18/F15）。删除语义为墓碑传播 + 水位线 GC，路径顺序（清单先落、对象后删）正确。
3. **断点续传 / 冲突解决 / 增量同步**：续传前提确定性 nonce（F11）+ S3 原生分片（F12）+ WebDAV 自造分片协议（F13）复核在位；冲突裁决 LWW+version 平局、墓碑、复活、冲突副本留档账本齐备，本轮修复的是**失败传播层**（F16/F17）而非裁决层——裁决逻辑未发现新缺陷；增量差量（桶指纹 + epoch 快跳 + 本地账本快照）修复清单替换与 epoch 说谎两处（F14/F16）。
4. **性能**：未变桶零流量、空库守卫 COUNT 化（前轮 F2）、64 桶封顶下表级重哈希代价 O(行数) 仅发生在内容变更时；CAS 冲突重算上限 3 轮，无放大。未发现本轮需修的新瓶颈。
5. **安全**：E2E（AES-256-GCM + zstd + PBKDF2 600k 单调不降级）、密钥指纹日志仅 SHA-256 前缀（无裸密钥材料）、空数据覆盖守卫、KeyMismatch fail-closed 矩阵在位。「指纹密钥无关」是设计属性（指纹用于差量非保密），正解是 force 路径而非改指纹口径（F15）。两个密码学强度项延后见 §四 N36/N37。
6. **日志与可观测性**：sync_history 落库（模块计数/冲突数/错误清单，前轮 F9）、progress 事件序列完整、本轮补 push 表失败 warn（F20）。残留窄项（历史仅存首错、progress 尾段 90% 封顶、无取消 API）见 §四。

## 四、确认存在但本轮不修的项（含定级与理由）

| # | 定级 | 问题 | 不修理由 |
|---|---|---|---|
| N9 | P3 | 上一版清单回滚点 `manifest_prev.orsync` 每轮无条件覆写，连续两轮 CAS 冲突后真正的「同步前版本」已不可得 | 回滚点定位是诊断便利而非数据保护（清单可由桶对象重建）；区分「首写者」需条件写 prev，流量翻倍不值得 |
| N10 | P3（存疑） | WebDAV `upload_conditional` 不先 ensure_directory：基目录被外部删除后清单条件 PUT 持续 409 | 正常流程数据桶上传先于清单、目录必已建立；触发需外部删目录且此前无任何普通 PUT，409 自愈（F8）已覆盖普通 PUT 路径。列观察项，与 N11 一并处理才有价值 |
| N11 | P3 | S3 `put_conditional` 把 409 与 412 同样映射 PreconditionFailed（409 实为父资源缺失，两因混淆） | 无论哪种归因，CAS 重算 + 回读校验都收敛到正确判定；区分仅改错误文案，零行为差异 |
| N13 | P3 | 回收站 purge 物理 DELETE 与墓碑水位线 GC 的窗口：极慢设备可能在下轮 pull 前错过已回收墓碑 | 属水位线机制的既有边界（所有设备检查点约束在先）；F14 后墓碑索引桶级合并已消除更大的一类丢失。收紧需设备检查点上报频率联动，规模未到 |
| N14 | P3 | 部分表失败时 `last_synced_at` 仍刷新 | 该字段语义是「最近一次同步尝试完成时间」（UI 展示 + 调度水位），无任何判定依赖其精确性 |

| N18 | P2 | 附件 push 内部失败只进 `errors` 向量不抛 Err，外层 `with_retry` 对附件失败等效空转 | 附件已有**分片级**重试（F12/F13 单片独立重传），整模块业务重试会对其余已完成分片重复 HEAD 探测，加剧坚果云限流；维持分片级为唯一重试层 |
