# 循迹（Orbit）全面评估与优化方案（2026-10-18）

> **性质**：只读评估 + 候选方案，**本阶段不包含任何代码修改**。本文不新建 backlog，`docs/07 §五` 仍是唯一状态源；圈选后按 07 的表格式新增行并顺延编号（当前最大 #87，下一编号 **#88**）。
>
> **输入证据**：仓库源码与 DDL（迁移 `0001`–`0007`）、内存门禁基线（`perf-metrics/baselines.json`，2026-09-18 实测）、`docs/07`/`09`/`10`/`11`/`12`、2026-Q4 十二款产品公开资料对标（含未入库的 `todo-feature-benchmark-2026/` 报告）、各产品官方文档/帮助中心（OmniFocus Review、Todoist Filters 等）。
>
> **口径**：源码/DDL/测试 > 门禁实测 > 项目文档 > 外部资料。外部竞品能力未逐一真机复测，文中凡属"公开资料口径"均按能力存在性引用，不引用具体版本号。

## 一、结论摘要（TL;DR）

**Orbit 的功能面已经越过"补齐对标清单"阶段。** 截至 2026-10-17：

- 桌面/移动双端对齐批次 G1–G16 已全部收口（`docs/12`；G11–G16 为 2026-10-18 第三批）；
- TickTick 对标 G1–G5 与 M8–M10 已落地，G6/G8 为有意不跟进（`docs/07 #81–#86`、`docs/11`）；
- 内存专项 A 系列除"下一波未知项"外无遗留，桌面 10k 门禁全绿（`docs/09`）；
- 搜索已是 FTS5 trigram + 短词 LIKE 回退，**不是缺口**；Android 分享捕获、图片缓存上限、相对提醒、时间块、多层子任务、项目文件夹均已存在。

**剩余空间不在"有没有"，而在三件事：**

1. **大对象整包操作**——全量备份/恢复、CSV/ICS/明文导入、附件加解密、同步整表装载，仍存在与数据总量成正比的整块缓冲；这是当前最明确的**峰值内存风险**，且移动端把整份备份以 `List<int>` 跨 FRB。
2. **维护闭环的深度**——已有"一次性周回顾"，但没有**项目级回顾节奏/回顾记录**，也没有**收件箱分诊（Inbox Triage）**；对标 OmniFocus Review、Things Inbox 的"澄清"环节仍是空白。
3. **规模化与可测性**——单次加载上限硬编码 10k（双端一致），50k 场景未验证；冷启动缺本机可信基线（`docs/09` 明确"无可靠数值"）；移动端只有诊断页展示 RSS，没有可重复的内存门禁。

**建议的五项最高价值动作：**

| 优先级 | 动作 | 解决的问题 | 预估 |
|---|---|---|---|
| P0 | 全量备份/恢复 v2 流式化（保留 v1 读兼容） | 峰值内存与备份包大小解耦；移动端不再搬运整包字节 | 5–8 人日 |
| P0 | 导入限额 + 流式解析（CSV/ICS/明文） | 大文件导入可被内存打爆且无友好上限 | 2–3 人日 |
| P0 | 移动端内存门禁 + 桌面基线刷新 | 当前只有桌面有可重复门禁，移动端是盲区 | 3–5 人日 |
| P1 | 项目回顾节奏 + 收件箱分诊 | GTD 维护闭环；直接复用现有任务写路径，零协议风险 | 6–9 人日 |
| P1 | 本地启发式日排程（非云端 AI） | 时长/容量字段已落地但缺少消费端；本地、可解释、可撤销 | 5–8 人日 |

**明确不做**：位置提醒、云端 AI 排程、协作/共享、番茄钟/习惯、日历订阅、倒数日、底部 Tab 改版、i18n/Web。理由见 §十一。

## 二、评估方法与证据等级

| 等级 | 含义 | 本文用法 |
|---|---|---|
| A | 源码/DDL/测试直接证明 | 结论可直接作为实施依据 |
| B | 仓库内可复现的门禁/实测数据 | 作为基线与验收判据 |
| C | 项目文档/外部公开资料 | 作为方向参考，实施前需复核 |

**本次核查的关键事实（A 级）：**

- 双端任务列表单次上限均为 10,000：`apps/desktop/src/features/todo/shared/constants.ts:46`、`apps/mobile/lib/modules/todo/providers/todo_providers.dart:91`；超出时双端都有"列表不完整"条幅（`task-panel.tsx:282`、`sub_list_screen.dart:3014`）。
- 搜索：`business_api::search_all` 对 ≥3 字走 FTS5（trigram），1–2 字走 LIKE 回退（`crates/orbit-core/src/api/business_api.rs:984` 起）；FTS5 表与触发器在 `0001_init.sql` 约 660–769 行。
- 备份：`export_full_sync_backup_inner` 把每张表的全部行序列化成 `String`，汇总到 `BTreeMap<String, String>` 后再 ZIP + AES-GCM 编码（`crates/orbit-core/src/api/full_sync_backup_api.rs:193–383`）；导入入口 `import_full_sync_backup(..., bytes: &[u8], ...)` 接收整包字节（同文件 :621）；云端下载返回 `Vec<u8>`。
- CSV：`parse_csv(content: &str)` 整份解析，预览与执行都先把全部行映射进内存（`crates/orbit-core/src/api/csv_import_api.rs:34`、`:362–406`），未见文件大小/行数硬上限。
- 附件：`asset_api.rs:251` 使用 `std::fs::read` 整文件读入；单文件上限 50MB、单任务 20 个（`docs/07 #33`）。
- 同步：`load_table_items` 走整表 `SELECT *`；N52 的 `load_table_items_of` 已支持按 uuid 分批（每批 500）装载（`crates/orbit-core/src/cloud_sync/db_loader.rs:45–147`）。
- 移动端本地备份预览走 `fullBackupPeekLocal(List<int> bytes)`（`apps/mobile/lib/data/api/orbit_bridge.dart` 约 :563），整份文件跨桥。
- 桌面基线（B 级，2026-09-18 强制 GC 口径）：10k 行 used heap **37MB**（阈值 42，目标 60）、total heap 69.3MB、2.9KB/行、DOM 863 且斜率为 0、RSS 354MB（阈值 390，目标 350）、20 次勾选后泄漏 6MB、切视图峰值 61.3MB、churn 峰值 83.1MB（`perf-metrics/baselines.json`）。
- 移动端图片缓存已限 300 个/60MB（`apps/mobile/lib/main.dart:44–46`），不是无界缓存；Android `ACTION_SEND` 分享捕获已实现（`AndroidManifest.xml:64`、`MainActivity.kt:84`）。
- NLP 快速输入已支持"今天/明天/后天/大后天、周X、下周X、!优先级、#项目、@标签"，**不含**时刻、时长、重复规则（`apps/mobile/lib/modules/todo/logic/parse_quick_input.dart:7–16`）。
- 迁移当前最大编号为 `0007_subtask_parent.sql`；新 DDL 从 `0008` 起。

**局限**：外部对标报告为未入库的静态 HTML，部分竞品能力来自评测/帮助文档而非真机；本文对"竞品是否支持某能力"只作方向性引用，立项前应按仓库既有惯例做一次真机/官方文档复核。

## 四、竞品对标结论（十二款产品，十个模块）

### 4.1 模块级能力分布（择要）

| 模块 | 领先者 | Orbit 现状 | 判定 |
|---|---|---|---|
| 捕获 | Todoist（自然语言）、Things 3（快速录入）、系统级分享 | NLP 日期/优先级/项目/标签；全局快捷键；分享 | 对齐；缺"时刻/时长/重复"的 NLP |
| 组织 | Todoist（过滤器）、OmniFocus（透视） | 项目层级、标签、保存筛选器、四象限、看板、表格 | 对齐 |
| 规划 | OmniFocus（Forecast/Review）、Structured（时间轴）、TickTick（日历） | 日历月/周/议程/时间轴、时长、容量条、周回顾 | 接近；缺"项目级回顾节奏"与"自动排程建议" |
| 提醒 | TickTick（持续/摘要）、Apple（位置/自然语言） | 多提醒、相对档、持续、摘要、通知历史 | 对齐（位置提醒有意不做） |
| 执行 | Microsoft To Do（My Day）、Things（Today） | 我的一天、今日上下文条、容量 | 对齐 |
| 回顾统计 | OmniFocus Review、Todoist Karma、滴答统计 | 统计仪表盘、热力图、周回顾向导 | 统计对齐；**周期回顾机制缺失** |
| 协作 | Todoist/Superlist | 无 | 有意不做 |
| 习惯/专注 | TickTick/Things | 无 | 有意不做 |
| 集成/隐私 | Google/Apple（生态）、Orbit（加密+自托管） | 三协议同步、零遥测、明文导出 | **反超项** |
| 平台 | Apple 全平台、TickTick 全平台 | Windows/macOS/Linux/Android；iOS 待验收 | 发布工程项，不是功能缺口 |

### 4.2 真实的产品级差距（剔除排除项后）

1. **项目级回顾节奏与回顾记录**：Orbit 的周回顾是"一次性向导"（#83/#86），没有每个项目自己的回顾周期、上次回顾时间、到期徽标与回顾历史。OmniFocus Review 是唯一成熟标杆（公开资料口径），其余产品多为方法论/教程。
2. **收件箱分诊**：Orbit 有"未分组"作为事实收件箱，但没有"逐条澄清"的全屏流程；Things Inbox / OmniFocus Inbox 的"捕获→澄清"是 GTD 的关键第二步。
3. **本地启发式排程**：G4 容量条只回答"今天排了多少"，不回答"先做哪个、放在几点"。Motion/Reclaim/Sunsama 走云端 AI（与定位冲突），但"本地规则 + 可解释 + 可撤销"的轻量排程不冲突，且 Orbit 已有 `duration_minutes` 地基。
4. **拼音/首字母搜索**：FTS5 对中文子串有效，但"gzs → 工作总结"这类拼音首字母检索没有实现。是否内置属竞品未复测项，但中文用户预期明确，建议先做技术验证再决定。
5. **NLP 时刻/时长/重复**：现有解析器覆盖日期、优先级、项目、标签，未覆盖"明晚 8 点""30 分钟""每周一"。这是捕获效率的最后一公里。

### 4.3 讨论过但不单独立项

- **Forecast/未来 7 天视图**：日历议程 + 周快捷视图 + 时间轴 + 计划排程已覆盖大部分场景，单独再造一个"预测"页会形成第四个日期视图，信息架构收益低于维护成本；建议并入 F3 排程预览。
- **日历订阅 URL**：与零遥测叙事冲突，`docs/10` C-1 / `docs/11` M12 维持不启动。
- **倒数日**：`docs/07 #76` 已撤回；AGENTS.md 明确属生活记录域。
- **邮件转任务**：需云端邮件通道与账号，冲突。
- **AI 摘要/语音**：平台 STT 可能联网，零遥测叙事冲突。

## 五、功能扩展方案（F 系列）

> 原则：优先复用既有写路径与 UI 原语；新增 DDL 必须带 `DEFAULT`、行尾中文注释、增量迁移；新增同步表必须同步更新 `SYNCABLE_TABLES` 与 `modules.rs` 计数断言；能不改协议就不改。

### F1 项目回顾节奏与回顾中心（P1）

**问题与证据**：周回顾已产品化，但回顾的粒度是"全局一次"，项目本身没有节奏。GTD 的 Review 本质上是**按项目**检查"目标是否仍有效、下一步是什么"，OmniFocus 的 Review 透视即为标杆。

**现状**：`todo_projects` 无回顾字段；`#83/#86` 的 `collectWeeklyReview` 只按逾期/无日期/停滞三类归集任务。

**方案要点**：

1. DDL `0008_project_review.sql`：
   - `todo_projects.review_interval_days INTEGER DEFAULT 0`（0=关闭；7/14/30 等）
   - `todo_projects.review_last_at INTEGER DEFAULT NULL`（毫秒）
   - 可选 `review_snooze_until INTEGER DEFAULT NULL`（暂缓到某日）
   - 不新增同步表：`todo_projects` 已在同步白名单内，列随整行同步；避免白名单计数与合并顺序的新风险。
2. Core API（`project_review_api` 或并入 `business_api`）：
   - `list_projects_due_for_review(now)`：纯查询 + `review_due_at` 纯函数（本地时区日界，闰月/跨年安全）；
   - `mark_project_reviewed(project_id)`：写 `review_last_at=now`，emit db-change；
   - `set_project_review_interval(project_id, days)`；`snooze_project_review(project_id, until)`。
3. 双端 UI：
   - 侧栏项目行"待回顾"徽标；侧栏/统计入口进入"回顾中心"；
   - 回顾中心按逾期天数排序，逐项目进入向导：**目标是否仍成立 → 清理完成/停滞项 → 确认下一步 → 标记已回顾**；
   - 周回顾向导第一步插入"项目回顾"（可跳过），不改变既有三步的任务处置逻辑；
   - 项目编辑页增加"回顾周期"下拉（关闭/每周/每两周/每月）。
4. 移动端对称：复用 `showSelectBottomSheet` 与既有项目编辑抽屉，不新增导航结构。

**不做**：v1 不建独立回顾日志表（历史价值低于同步面成本）；若后续需要"回顾备注/审计"，再评估本地只读表。

**验收**：到期判定在跨时区/跨 DST/月末场景正确；标记回顾后徽标消失且下次到期日正确；周回顾可跳过项目步骤；双端数据一致；Rust 纯函数单测 + 双端各 2 例 widget/组件测试。

**风险/工作量**：低风险，3–5 人日。

### F2 收件箱分诊（Inbox Triage）（P1）

**问题与证据**：捕获已经很顺（NLP、分享、全局快捷键），但"未分组"只是一个筛选结果，没有把"逐条决定归属"变成流程。Things/OmniFocus 的 Inbox 是捕获后的默认落点，澄清是 GTD 的核心动作。

**现有地基**：`project_id IS NULL` 即未分组；任务更新、批量移动项目、改日期、标签关联、删除/撤销均已有 API 与 UI 原语。

**方案要点**：

1. 零 DDL、零新协议：新增查询/入口，复用 `todoTaskUpdate`、`todoTaskDelete`、标签关联、批量移动。
2. 桌面：全屏"分诊"视图（或大尺寸抽屉），一次一张卡片/一行：
   - 快捷键：`1–9` 选项目、`T` 今天、`M` 明天、`N` 无日期、`P` 优先级、`Enter` 下一条、`S` 跳过、`Backspace` 退回；
   - 顶部进度："待分诊 N 条 · 已完成 M 条"；结束给出汇总。
3. 移动：全屏页 + 底部抽屉选择；左右滑分别为"跳过/下一条"（沿用现有手势语义），点击卡片展开字段行；所有写操作走现有 bridge。
4. 可逆性：每条动作推入撤销栈（复用通用撤销），删除走 5s 撤销窗口/回收站。
5. 入口：侧栏"未分组"行内的"开始分诊"、项目列表空态、周回顾"收件箱清零"步骤。

**验收**：连续分诊 50 条不离开页面；每条动作可撤销；分诊后未分组计数正确；键盘全流程可完成；移动端单手可达；无新增内存常驻容器。

**风险/工作量**：低风险，3–4 人日（双端）。

### F3 本地启发式日排程（P1，先只读预览）

**问题与证据**：`duration_minutes` 与容量条已落地，但排程仍完全手动。云端 AI 排程（Motion/Reclaim）与零遥测冲突；本地确定性规则可以覆盖"今天先做什么、放几点"的高频诉求，且可解释、可撤销。

**边界**：**不是** G8 的云端 AI；不联网、不调用模型；不自动写入，必须先预览再应用。

**方案要点**：

1. 输入与配置：
   - 任务：今日到期/逾期/我的一天/未排期且带时长的任务；优先级、截止时刻、项目、预计时长；
   - 偏好：工作开始/结束时间、午休、最小粒度（15 分钟）、是否包含逾期、每日预算（复用 G4 的 `todo_capacity_budget_minutes` 语义）；
   - 偏好存 `cfg_kv`（本地，不参与同步；每台设备可有自己的作息）。
2. 算法（Rust 纯函数，双端同口径）：
   - 硬约束：不排到过去；不违反带时刻的截止；不重叠；固定时长放不下则延后；
   - 排序：逾期 → 今日截止（按截止时刻 EDF）→ 优先级 → 我的一天 → 其余；同优先级内短任务优先填充空档；
   - 输出：`Vec<PlanSlot { task_id, start_ms, end_ms, reason }>` + 未排入清单 + 超载提示；
   - 确定性：相同输入相同输出，便于测试与解释。
3. 应用语义（关键）：
   - 应用时写 `my_day_date=计划日` + `start_date=时段起点`，**不修改 `due_date`**；
   - 单事务批量写入，emit db-change；保存应用前快照用于撤销；
   - 用户可逐条勾选应用，默认全选但可取消。
4. UI：
   - 桌面：今日上下文条旁"规划今天"入口 → 预览抽屉/面板，时间轴展示，理由徽标（"截止最近""优先级高""填空档"）；
   - 移动：底部抽屉 + 时间轴预览，沿用时间轴视觉；应用后 Toast + 撤销。
5. 分阶段：阶段一纯预览（只读，1–2d 可验证价值）；阶段二应用写入；阶段三偏好编辑/多日规划（按反馈决定）。

**验收**：黄金用例（跨午休、超载、截止时刻、无时长任务）全绿；计划结果确定性；应用幂等；撤销恢复原 `start_date/my_day_date`；10k 任务规划 < 200ms；全程无网络请求。

**风险/工作量**：中风险（语义定义比算法更难），5–8 人日。

### F4 NLP 补时刻/时长/重复（P1）

**问题与证据**：现有解析器支持日期、优先级、项目、标签（`parse_quick_input.dart:7–16`），但不支持"明晚 8 点""30 分钟""每周一"。捕获效率是待办应用的分水岭，且无需 DDL。

**方案要点**：

1. 新增语法（双端逐字同口径）：
   - 时刻：`HH:mm`、`上午/下午/晚上 8 点`、`8 点半`、`明晚 8 点`；有日期则组合，无日期默认今天（已过则明天）；
   - 时长：`30 分钟`、`1 小时`、`1.5 小时`、`2h`；写入 `duration_minutes`；
   - 重复：`每天`、`每周X`、`每月X号`；映射现有 `repeat_*` 列；只在表单新建预览，不自动保存。
2. 解析纪律：长词优先、命中区间互斥、未匹配 token 原样保留（沿用现有规则）；歧义时不猜测，保留原文。
3. 双端一致性：新增共享测试向量（JSON），TS 与 Dart 各跑同一组输入/期望；避免两套解析器漂移。
4. 预览：表单 chips 显示"截止：明天 20:00 · 时长：30 分钟 · 重复：每周一"，用户可逐项取消。

**验收**：既有 17 例不回归；新增 ≥30 组向量双端一致；时区/DST 边界正确；保存结果与预览一致。

**风险/工作量**：中风险（歧义与双端漂移），3–4 人日。

### F5 拼音/首字母搜索（P2，先 spike）

**问题与证据**：搜索已是 FTS5 + LIKE 回退，但中文拼音首字母检索未实现。"gzs → 工作总结"是中文用户的高频预期；不过竞品是否内置需真机复核，故先做技术验证。

**方案要点（推荐 A）**：

- A. 本地派生索引：新增**不同步**的 `search_pinyin` 表（`uuid`、`pinyin_full`、`initials`），由 Rust 写路径统一维护 + 启动幂等回填；查询时把拼音输入展开后与 FTS 结果合并排序。表不进 `SYNCABLE_TABLES`，重建/删除不影响业务数据。
- B. 查询时对当前内存任务集做转写：省 DDL，但 10k/50k 下 CPU 与内存不可控，不推荐。
- Spike 门限（1–2 人日）：
  - pinyin crate 的体积/许可证/多音字策略可接受；
  - 10k 条回填 < 2s，索引磁盘 < 5MB；
  - 首字母查询 p95 < 100ms；
  - 不显著抬高启动内存。
  - 任一不达标则**不做**，保留 FTS 现状。

**验收**：`gzs`/`gz`/全拼均可命中；结果排序不劣于现状；索引可重建；删除/软删后无幽灵命中；内存审计无新增无界容器。

**风险/工作量**：中高风险，4–6 人日（含 spike）。

## 六、内存优化专项（M 系列，本文重点）

### 6.1 现状与风险清单

桌面内存治理已成熟：门禁三件套（增长曲线 / 无界审计 / exe 差分）、阈值只紧不松、A14 后 10k used heap 37MB、DOM 斜率 0。**当前问题不是已知泄漏，而是"整包/整表缓冲"与"移动端无门禁"。**

| # | 热点 | 证据 | 风险 |
|---|---|---|---|
| 1 | 全量备份导出 | 每表全量 JSON 字符串汇总 `BTreeMap`，再 ZIP + AES-GCM（`full_sync_backup_api.rs:193–383`） | 峰值 ≈ 数据库 JSON + ZIP + 密文多份；与库大小线性相关 |
| 2 | 全量备份导入/预览 | `import_full_sync_backup(bytes: &[u8])`；`peek` 也接收整包；云端下载 `Vec<u8>` | 大备份直接打爆内存；移动端 `List<int>` 跨 FRB 双份 |
| 3 | CSV 导入 | 整份 `String` + 全部映射行；无大小/行数上限（`csv_import_api.rs:34`、`:362`） | 用户可导入任意大文件；预览也全量映射 |
| 4 | ICS/明文导入 | `bulk_import_records_from_values` 接收整批值 | 批量 JSON 常驻；需确认双端传参形态 |
| 5 | 附件 | `std::fs::read` 整文件；AES-GCM 整块；50MB/文件 | 单文件峰值多份；4 路并发上传叠加 |
| 6 | 同步整表装载 | `load_table_items` 全表 `SELECT *`；N52 已提供按 uuid 分批路径 | 大表首同步/重建时整表驻留 |
| 7 | 无界审计提示 | 18 组 `sql-fetch-all` 提示（非阻断） | 需分类：合法的全表导出 vs 可流式的读路径 |
| 8 | 移动端 | 仅诊断页 RSS；无门禁/趋势；10k 全量跨 FRB | 回归不可见 |

> 说明：`perf-metrics/audit-unbounded.mjs` 的 `sql-fetch-all` 当前是提示级（blocking:false），**不是失败**；本方案主张先分类、再对真正的大表读路径加限/流式，而不是一刀切改掉所有 `fetch_all`。

### 6.2 总体原则

1. **峰值与数据总量解耦**：备份/导入/附件/同步的峰值应由分块大小决定，而不是由库大小决定。
2. **先测后定**：每一类操作先建立可复现的峰值基线，再锁定目标；不拍脑袋写阈值。
3. **不为省内存牺牲正确性**：备份仍要校验表读取失败（F71 口径）、导入仍要逐行独立成败、附件仍要内容寻址与原子落盘。
4. **临时文件优先于内存**：大对象走临时文件 + 流式管道；文件用后即删，异常路径也要清理。
5. **移动端不搬运整包**：FRB 传路径/流句柄，不传 `List<int>`。
6. **门禁只紧不松**：`baselines.json` 的 thresholds 不因新功能放宽；新增操作纳入独立基线文件。

### M1 全量备份/恢复 v2 流式化（P0，5–8 人日）

**目标**：备份/恢复峰值内存与库大小无关；保持 `.orfullsync` / `.waitfullsync` 读兼容。

**方案要点**：

1. **容器 v2**：新 magic/version（例如 `OFS2`），manifest 先行；正文按固定帧（建议 4MiB）AES-256-GCM 加密，帧 nonce 由基础 nonce + 帧序号派生，帧头带序号并作为 AAD，防重排/截断；manifest 记录帧大小、明文摘要、各表行数。
2. **导出**：
   - 逐表按主键/rowid 分页读取（每批 500–1000 行），直接写入 ZIP entry 的流式 writer；
   - 边写边算明文摘要；ZIP 写入临时文件，再按帧加密到目标临时文件，最后原子重命名；
   - 云端上传改为文件流/分片（S3 multipart、WebDAV 流式 PUT），本地写入从同一临时文件复制；不再共享一整块 `encoded.bytes`。
3. **导入/预览**：
   - `peek` 只读并解密 manifest 帧，返回设备/表计数/版本；不读正文；
   - 导入时流式解密到临时 ZIP，逐表流式解压并分批写入；单事务提交，失败回滚；行数与 manifest 校验；
   - 恢复前仍保留现有"危险分级 + 两段式确认 + 5s 时停"。
4. **兼容策略**：v2 默认写；v1 读路径保留（golden fixture 覆盖）；旧版本应用无法读 v2 属预期，需在发布说明中标注"备份格式升级，旧版无法恢复新备份"。
5. **移动端**：桥接改为 `fullBackupPeekPath(path)` / `importFullSyncBackupPath(path)` / 导出返回文件路径；file_picker 关闭 `withData`；分享/另存走系统文件。
6. **ADR**：新增 `docs/adr/0008-backup-streaming-format.md`，记录格式、帧大小、兼容与回滚。

**验收**：

- 构造 200MB 级备份（10k 任务 + 大附件/大评论）导出/导入；
- 峰值增量 RSS ≤ 128MB 且**不随备份体积增长**（用 2 个不同体量样本对比斜率）；
- v1 样本可恢复，v2 往返后数据逐表计数/摘要一致；
- 断点/异常中断不留下半恢复数据库；临时文件清理；
- 云端三协议上传回归。

**风险**：格式兼容与云端适配器是主要风险；分两批（本地流式 → 云端流式）落地，第二批可回退为"临时文件读出后整块上传"。

### M2 导入限额 + 流式解析（P0，2–3 人日）

**范围**：CSV、ICS、明文 JSON 导入。

**方案要点**：

1. 统一入口先做**文件大小/行数硬上限**（建议 CSV 20MB / 200k 行，ICS/JSON 同量级；具体值按真实用户样本定），超限给出可读错误与建议（拆分/清理）。
2. 预览：只解析并保留前 N 行（建议 200），统计仍全量流式扫描；不再把全部映射行驻留内存。
3. 执行：流式逐行解析，每 200 行一个事务批次；提供进度事件与取消标记；单行失败不影响其他行（保持现有语义）。
4. 桥接：桌面/移动传文件路径（移动关闭 `withData`），Rust 侧 `BufReader` 读取；避免 JS/Dart 先读整份内容再 invoke。
5. 双端 UI：选择文件后先显示大小与预估行数，超限即拦；导入中显示进度与取消。

**验收**：50MB CSV 被明确拒绝且应用不卡死；100k 行导入峰值增量 ≤ 64MB；预览内存 < 5MB；取消后无半写状态；现有三档 CSV 预设与逐行说明不回归。

### M3 附件分块加解密与上传（P1，3–5 人日）

**方案要点**：

1. 写入：流式计算 SHA-256 + 分块 AES-GCM 写临时文件，完成后原子重命名；不再 `fs::read` 整文件。
2. 读取/预览：解密到临时文件供系统打开；图片预览限制尺寸/缩略图，避免整图解码常驻；预览缓存沿用 Flutter 300/60MB 上限。
3. 同步：上传下载改流式/分片；4 路并发降至 2 路并按总字节预算做背压（可配置）。
4. 兼容：附件容器格式需带版本；旧附件读路径保留；内容寻址 hash 不变。

**验收**：50MB 附件上传/下载峰值增量 ≤ 32MB；并发 4 个不叠加为 4 份整块；旧附件可读；GC/删除行为不变。

### M4 同步装载流式化与审计分类（P1，3–5 人日）

**方案要点**：

1. 全表路径（`load_table_items`）改为按桶/主键分批读取、序列化后立即释放，避免整表 `Vec<Value>` 常驻；N52 行级路径保持。
2. 对 18 组 `sql-fetch-all` 提示逐项分类：
   - 合法全表：备份导出、明文导出（后续随 M1 流式化）；
   - 可加 `LIMIT`/分页：列表、模板、筛选器、回收站等读路径；
   - 只读聚合：统计可流式累加，不物化全表。
   - 在审计脚本允许的注释标记基础上，对确认无界且不修的点登记 `knownUnbounded`（只减不增），不静默忽略。
3. 建立"大表读路径清单"文档，后续新增 `fetch_all` 必须说明数据上界。

**验收**：50k 任务首同步峰值增量 ≤ 128MB；同步耗时回归不超过 10%；审计提示数量下降且无新增阻断项。

### M5 移动端内存门禁与预算（P0，3–5 人日）

**方案要点**：

1. 建立可重复脚本（本地 release 门禁，不进 CI 设备矩阵）：
   - 场景：冷启动、10k 列表滚动、日历月/时间轴、全量备份导入/导出、附件预览、搜索；
   - 采样：`adb shell dumpsys meminfo <pkg>` 取 RSS/PSS，3 次中位数；
   - 产物：`perf-metrics/mobile-baselines.json`（阈值/目标/测量口径），与桌面 `baselines.json` 同构。
2. 应用内诊断增强：诊断页增加"当前/峰值 RSS"采样按钮与最近一次场景标记；不放后台常驻采样器（避免自身成为内存负担）。
3. 先测后设阈值；首批目标建议：10k 列表增量 RSS 与桌面同量级、备份/导入在 M1/M2 后与文件大小解耦。
4. 代码侧门禁：CI 增加静态检查/测试，禁止新增"整文件 `List<int>` 跨桥"的公开 API（以 bridge 接口清单断言）。

**验收**：基线文件入库；6 个场景可复跑；回归超过阈值时脚本非零退出；诊断页可复现读数。

### M6 桌面基线刷新与操作级探针（P0，1–2 人日）

**方案要点**：

1. 在 M1–M4 落地后重跑 `growth-curve --gate`、`audit-unbounded --gate`、`memory3 --gate`；`--record` 只回写 measured，**不改 thresholds**。
2. 新增操作级探针（脚本，非产品代码）：备份导出/导入、CSV 导入、附件上传的峰值 RSS/堆增量，写入 `perf-metrics/operation-baselines.json`。
3. 冷启动与搜索延迟测量并入性能专项（§七），不与内存阈值混用。

**验收**：基线刷新有记录；三项门禁绿；操作级探针有可复现数值；docs/09 增补"下一波"章节。

### M7 渲染与缓存护栏（持续）

- 新增列表/分组一律走虚拟化（现有 `domNodesSlope_per_1k=30` 哨兵继续有效）；
- 50k 场景引入窗口化加载（§七 P1），避免把 50k 行一次性塞进 React Query；
- 不全局下调/上调 `gcTime`；任何缓存策略调整必须用 growth-curve 的 `switchChurn`/`extraCopyCostMB` 连测；
- 移动端图片缓存已有上限，不重复造轮子。

### 6.3 内存验收目标（Phase 0 实测后锁定）

| 场景 | 现状 | 目标（首版） | 测量 |
|---|---|---|---|

## 七、性能优化专项（P 系列）

### P1 50k 规模档（P2，5–8 人日）

**现状**：双端单次 10,000 条上限，超出即提示"列表不完整"；React 侧虚拟化已把 DOM 斜率压到 0，但 DTO 数组、过滤/排序、序列化仍与行数线性相关。移动端同样 10k 全量跨 FRB。

**方案要点**：

1. Core 列表 API 增加**键集分页**（cursor = 排序键 + id），保留现有 filter/sort 参数；返回 `items + next_cursor + total`；
2. 桌面列表改为窗口化加载（首屏 500–1000 行，滚动预取下一页）；虚拟器保持；分组置顶段同样虚拟化；
3. 看板/表格/四象限按列/分区窗口化；日历只查可见范围；
4. 拖拽重排仅在已加载窗口内允许，跨窗口拖拽给出提示（避免"看不见的行被重排"）；
5. 搜索保持服务端 FTS，不分页混入内存过滤；
6. 移动端列表改用分页 + `ListView.builder` 增量拉取（现有虚拟化基础上）。

**验收**（50k 种子库）：

- 首屏可交互 < 1.5s；滚动 p95 帧 < 20ms；
- used heap ≤ 120MB；DOM ≤ 1,200；无"列表不完整"条幅（改为"已加载 X / 共 Y"）；
- 筛选切换 < 300ms；搜索 p95 < 150ms；
- 10k 现有门禁不回归。

### P2 冷启动基线（P0 测量，P1 优化）

**现状**：`docs/07` 有 ~320ms 的说法，但 `docs/09` 明确本机无可靠数字；启动标记已存在，缺 10 次采样的 p50/p95。

**方案要点**：

1. 定义阶段：进程启动 → WebView ready → 首屏 paint → 首批数据 ready；桌面用现有标记 + 脚本采样；移动用 `am start -W` + 首帧回调；
2. 连续 10 次冷启动（清系统缓存/重启应用）取 p50/p95，入库 `docs/09`；
3. 优化候选（按测量结果取舍）：路由级懒加载、首屏非关键查询延后、避免重复 nav-data 请求、字体/图标按需、移动 BootGate 并行初始化；
4. 不以牺牲首屏正确性换数字；不引入后台轮询。

**验收**：基线入库；优化后 p95 改善 ≥15% 且无功能回归；文档不再使用未经本机验证的绝对值。

### P3 搜索延迟与索引维护（P1 测量）

- 建立 10k/50k 的 FTS 查询 p50/p95（含短词 LIKE 回退）；
- 大数据导入后执行 FTS `optimize`/`merge` 的时机评估；
- 若 F5 落地，拼音索引查询并入同一预算；
- 前端防抖保持 300ms，增加"过期响应丢弃"检查（防快速输入回跳）。

### P4 移动端帧率与启动（P2）

- profile 模式跑列表滚动、月历翻页、时间轴拖拽；
- 记录 build/raster p95 与 jank 比例；
- 仅针对实测瓶颈优化（如日历副标签重算、时间轴每帧布局），不做无证据重构。

### P5 数据库维护（P3）

- 现有 WAL checkpoint / VACUUM / 附件 GC 已具备；
- 评估启动/关闭时 `PRAGMA optimize` 与导入后 `ANALYZE` 的收益；
- 不改连接池 3 与 cache_size 8MB 的既有口径，除非有实测证据。

### U1 回顾中心（配合 F1）

## 十一、风险、约束与明确不做

### 11.1 风险与控制

| 风险 | 影响 | 控制 |
|---|---|---|
| 备份格式升级不可逆 | 旧版无法读新备份 | v2 写/v1 读双轨；发布说明显著标注；保留回滚版本；golden fixture |
| 云端适配器不支持流式 | 上传仍需整块 | 第二批落地；先本地流式；S3 multipart/WebDAV 流式验证；失败回退临时文件整块上传 |
| 移动 FRB 签名变更 | 生成物漂移/测试红 | 按 AGENTS 跑 codegen + `cargo fmt --all`；只 add 生成物路径 |
| 新增 DDL 与同步面 | 合并失败/计数断言红 | 优先加列不加表；新增表必须更新 `SYNCABLE_TABLES` + `modules.rs` 计数；内存库迁移测试 |
| 排程语义争议 | 用户不信任 | 先只读预览；理由可解释；默认不写；撤销；不做自动后台改写 |
| 拼音索引成本 | 内存/体积/多音字 | spike 门限，不达标即放弃 |
| 50k 改造面大 | 回归风险 | 先测量；窗口化与虚拟化分离提交；10k 基线守门 |
| 并发会话 WIP | 提交归属混乱 | 逐文件 add、提交后核对 `git log`；不回滚他人改动 |
| 估算偏差 | 排期失真 | Phase 0 先测量；每批结束复盘；不把目标当承诺 |

### 11.2 硬约束（不可违背）

- 本地优先/零遥测/无账号：F3 排程、F5 搜索全部本地完成，不新增网络依赖；
- E2E：新增派生索引/本地偏好不得进云同步明文；同步表变更按白名单流程；
- 迁移：`0001_init.sql` 冻结；新增 `0008+`；加列带 `DEFAULT`；破坏性变更走重建表；
- 内存：阈值只紧不松；新增累加容器必须有界标记；不引入后台常驻采样器；
- 兼容：`.orfullsync`/`.waitfullsync` 读侧兼容；附件旧格式可读；移动 mock 与 Rust 桥同口径。

### 11.3 明确不做（维持既有口径）

| 项 | 理由 |
|---|---|
| 位置提醒 / 地理围栏 | 持续定位与零遥测冲突（`docs/10` C-3） |
| 云端 AI 排程 / AI 摘要 / 语音 | 零遥测与无账号定位冲突；F3 只做本地规则 |
| 协作 / 共享 / 指派 | 单人定位（`docs/01 §二`） |
| 番茄钟 / 习惯追踪 | 偏离待办单一职责（`docs/07 §五`） |
| 日历订阅 URL | 外部轮询泄露存在性，`docs/11` M12 维持不启动 |
| 倒数日 / 重要日期 | 生活记录域，`docs/07 #76` 已撤回 |
| 底部 Tab 导航 / i18n / Web 版 | 与复刻蓝本/非目标冲突 |
| 自动写入的"AI 日程" | 可解释性与可控性不足；F3 坚持预览 |
