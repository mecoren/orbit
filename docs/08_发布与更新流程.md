## 一、qraft 流程解剖：可复用的七条

| # | 实践 | 关键机制 | 为什么值得复用 |
|---|---|---|---|
| 1 | **版本单一来源 + 同步脚本** | 只维护 `package.json#version`，`scripts/bump-version.sh` 同步 `Cargo.toml` / `tauri.conf.json`；前端版本经 Vite `define` 注入 `__APP_VERSION__`，源码零硬编码；脚本尾部打印「下一步清单」 | 消灭「手改漏一处」；版本号不再是散落常量，而是构建期注入的事实 |
| 2 | **两份更新日志同源双写** | `CHANGELOG.md`（仓库/GitHub 面）+ `src/lib/changelog.ts`（应用内「关于」面），同一次提交写完；把 0.2.7 漏写其一的历史事故直接写进规范 | 应用内「我装的是哪版」必须与仓库记录一致；教训显式化才不再犯 |
| 3 | **发版前置审计作业** | `audit` job 先于矩阵构建：`cargo audit` + `pnpm audit --prod`，用固定版本安装审计工具保证可复现 | 安全门禁放在最便宜的 job 里，失败不浪费 20 分钟矩阵时间 |
| 4 | **单点生成 `latest.json`** | 矩阵各平台只上传自身安装包与 `.sig`（`includeUpdaterJson: false`），构建全部结束后由独立作业读取各 `.sig` 内容合成唯一清单 | 全平台共享一份 manifest，矩阵并发「读 → 改 → 写」必然构成竞态（PATCH 命中被并发删改的 asset id → 404） |
| 5 | **dry_run 预演通道** | `workflow_dispatch` 输入 `dry_run`；`tagName` 置空时只构建、只传 artifact，不建 Release | 发版前能先验证「三平台可构建」，而不是拿真 tag 试错 |
| 6 | **发布作业幂等且崩溃安全** | 全程 Release **ID** 路由（tag 型端点对草稿恒 404）；manifest 上传走「临时名 → 删旧 → 改名」三步；资产上传 `--clobber`；失败可原样重跑 | 发布流水线一定会被重跑（网络/配额/人工），幂等是硬需求 |
| 7 | **流程写进 AGENTS.md 并绑定触发词** | 用户说「改版本号 / bump 到 X.Y.Z」，AI 编码工具按 6 步全流程执行（脚本 → 提炼 git log → 双日志 → CI 等价全绿 → 不主动提交 → tag 口径） | 流程不落在规范里，等价于不存在 |

qraft 项目中**不适用于本项目**的两条，明确不跟进：

- **资产改名规范化**（`normalize-assets` + `release-asset-map.sh`）：qraft 需要把 Tauri 默认产物名改成 `Qraft-x.y.z-Windows-Amd64-Setup.exe` 风格，于是必须让「清单 URL」与「改名后资产名」逐字节对齐。Orbit 接受 Tauri 默认命名，无改名需求 → 无此复杂度（代价：下载页文件名保持 `Orbit_0.1.0_x64-setup.exe` 形态）。
- **Windows/macOS/Linux 各双架构六平台矩阵**：qraft 覆盖 x64+arm64。Orbit 当前三平台（Windows x64 / macOS arm64 / Linux x64），扩矩阵是成本决策而非流程问题，见 §8。

## 二、优化前差距对照

| 维度 | qraft 实践 | Orbit 优化前 | 性质 |
|---|---|---|---|
| 版本来源 | 单一 `package.json` + 脚本同步 + 构建期注入 | **五处手工同步**（ADR 0004 §3），前端还有硬编码常量 | ⚠️ **已实际漂移** |
| 版本漂移实例 | — | `apps/desktop/package.json` 与 `about-page.tsx` 停在 `0.1.0`，`tauri.conf.json` / `pubspec.yaml` / 两处 `Cargo.toml` 已到 `0.1.1`（关于页显示的版本比实际安装版本低一档） | ⚠️ 已实际漂移，已于 2026-09-15 统一收敛到 `0.1.0` |
| 更新日志 | 两处同源双写 + 写进规范 | `CHANGELOG.md` 归档到 `[0.1.1]`（含 0.1.0/0.1.1 分段），应用内数组停在 `0.1.0`——0.1.1 未补记 | ⚠️ 已实际漂移（qraft 0.2.7 同型事故）；2026-09-15 将全部 git 记录归并为单一 `0.1.0` 条目 |
| 发版前置门禁 | `cargo audit` + `pnpm audit` job | 无（`ci.yml` 亦无审计作业） | 缺 |
| 发布触发 | tag 推送 + `workflow_dispatch` dry_run 预演 | 仅 tag 推送，无法预演 | 缺 |
| tag ↔ 版本一致性 | 清单从 `tauri.conf.json` 取版本，隐含要求一致 | 无任何校验，tag 名与清单版本可脱节 | 缺 |
| 更新清单 `latest.json` | 单点作业合成，崩溃安全上传 | `includeUpdaterJson: true` → 三平台矩阵并发读改写，PATCH 竞态 | ⚠️ 竞态风险 |
| updater 产物签名 | `createUpdaterArtifacts: true`，缺私钥即构建失败（刻意保护） | **未开启** → 无 `.sig`，清单签名字段为空 | ⚠️ **关键缺口**：应用内更新必然校验失败 |
| Release 发布态 | 直发（非草稿），`releases/latest/download/latest.json` 立即可用 | `releaseDraft: true` → endpoint 在人工点「Publish」前恒 404 | ⚠️ **关键缺口**：更新链路从未真正可用 |
| 附加资产上传 | 独立作业用 `gh release upload` 追加 | Android 独立作业用 `action-gh-release` 抢建 Release（会把 tauri-action 已发布的 Release 挤回草稿） | ⚠️ 风险 |
| `SHA256SUMS` | 未产出（Windows 依赖代码签名） | 有 job，但 `gh release download` 未注入 `GH_TOKEN`，失败被 `\|\| true` 吞掉后**写入占位文本**当清单 | ⚠️ 已坏：校验清单可能是假文件 |
| 应用内更新 UX | 安装方式识别（MSI/NSIS/便携）+ 不支持就地升级时兜底跳转 Release 页 | 手动检查 → 下载安装 → 重启三段式，无安装方式识别、无兜底跳转 | 部分差距（见 §8 遗留 #50） |
| 规范载体 | `AGENTS.md` 内成节 + `prd/14` 打包分发 | README §安装与更新 + ADR 0004（已过时：仍称「M5 无 updater」） | 缺规范节 |

## 三、优化后的流程

### 3.1 版本管理：单一来源 + 脚本同步

- **唯一数据源**：`apps/desktop/package.json#version`。
- **同步范围（脚本一把梭，禁止手改其余处）**：

  | 清单 | 用途 | 脚本动作 |
  |---|---|---|
  | `apps/desktop/package.json` | 源 | 写入新版本 |
  | `apps/desktop/src-tauri/tauri.conf.json` | 打包产物版本 + `latest.json` 版本来源 + tag 校验基准 | 同步 |
  | `apps/desktop/src-tauri/Cargo.toml [package]` | `CARGO_PKG_VERSION` → Rust 侧当前版本 | 同步（仅 `[package]` 段内，不碰依赖版本） |
  | 根 `Cargo.toml [workspace.package]` | `orbit-core` / `orbit-flutter` 版本 | 同步 |
  | `apps/mobile/pubspec.yaml` | Android `versionName` | 同步，`+build` 号每次发版自增 |
  | `Cargo.lock` × 2 | 两个 workspace 的本地包版本行 | 同步（漏改会让 `cargo --locked` 直接报错） |

- **前端不写死版本**：`vite.config.ts` 构建期注入 `__APP_VERSION__`（关于页/更新页消费）。
- **命令**：

  ```bash
  pnpm bump 0.2.0     # 升版：写源 + 同步全部清单 + 尾部打印发版清单
  pnpm bump:check     # 只校验一致性（零写入；CI 与本地通用）
  ```

- **版本语义**：`0.x` 阶段 minor = 功能批次、patch = 补丁；破坏性变更 bump minor 并在 CHANGELOG 显式标注。tag 恒为 `v` + 版本号（如 `v0.2.0`）；Android build 号只增不减。

### 3.2 变更记录维护：两份日志同源双写

| 面 | 文件 | 读者 | 发版动作 |
|---|---|---|---|
| 仓库/GitHub | `CHANGELOG.md` | 仓库读者、Release 正文引用 | 把 `[Unreleased]` 段改为 `## [X.Y.Z] - YYYY-MM-DD` 并新开 `[Unreleased]` |
| 应用内 | `apps/desktop/src/lib/changelog.ts` | 「关于 → 更新日志」 | 头部插入 `X.Y.Z` 条目（summary + changes 分类） |

- **提炼口径**：`git log v<上一 tag>..HEAD --oneline`，**按功能合并同类提交**，忽略 docs/chore/style 与纯过程性提交；版本边界以 tag 为准，不是日期。
- **护栏（自动化，不靠自觉）**：
  - `apps/desktop/src/test/release-consistency.test.ts`：五处清单 + 两个 lock + **应用内日志头部条目**都必须等于数据源版本，日期格式亦校验；
  - `pnpm bump:check`：发版前置门禁（`release.yml` 的 audit job 第一刀）。
- **不改历史段落**：`CHANGELOG.md` 已归档 1200+ 行且历史段落无 compare 链接，回填链接只会制造巨型噪音 diff；qraft 的 `[x.y.z]: …/compare/…` 约定**不采纳**。Release 正文引用 `CHANGELOG.md` 即可满足溯源。

### 3.3 发布触发条件

| 触发源 | 条件 | 行为 | 角色 |
|---|---|---|---|
| 日常 push / PR | `main` 分支 | `ci.yml` 三 job（web typecheck+vitest+build+e2e / rust-core check / flutter-mobile codegen+analyze+test） | 提交者 |
| 手动预演 | Actions → release → Run workflow，`dry_run=true`（默认） | 只构建、只上传 artifact，**不建 Release**（`tagName` 置空） | 发布者 |
| 正式发布 | push tag `v*`，tag 名 = 清单版本 | `release.yml` 全链路发布（见 §3.4） | 发布者 |
| 手动发版 | `workflow_dispatch` 于 tag ref 且 `dry_run=false` | 同上（用于流水线修好后重跑某个 tag） | 发布者 |

**进入正式发布的门禁（全绿才允许打 tag）**：

1. 本地 CI 等价检查全绿：`pnpm typecheck` / `pnpm test` / `pnpm e2e` / `pnpm lint:rust` /
   内存门禁 `node perf-metrics/audit-unbounded.mjs --gate` + `node perf-metrics/growth-curve.mjs --gate`
   （= `perf-gate` job，后者需先 `pnpm --filter orbit build`）；真机 exe 口径
   `node perf-metrics/memory3.mjs --gate` 不属任何 CI job，发版前对构建产物跑一次并把数字记进
   [09_内存与性能治理专项](09_内存与性能治理专项-2026-09-18.md)；
2. `pnpm bump:check` 输出 `VERSION_SYNC_OK`；
3. 两份更新日志已写完（护栏测试覆盖头部条目）；
4. `workflow_dispatch dry_run=true` 跑通一次（三平台可构建）；
5. `Secrets.TAURI_SIGNING_PRIVATE_KEY` / `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` 已配置（否则 audit job 直接失败并打印配置指引）。

> **tag 推送即发布**：Release 立即公开（非草稿），`releases/latest/download/latest.json` 立即可被存量客户端拉取。发错版本的回滚口径见 §7。

**Release 资产清单**：

| 资产 | 来源 | 是否进 `latest.json` |
|---|---|---|
| `Orbit_<ver>_x64-setup.exe`（NSIS）/ `…_x64_en-US.msi` / `…_aarch64.dmg` / `…amd64.AppImage` / `…amd64.deb` | tauri-action | ✅（各平台择一为主入口） |
| `*.sig`（minisign 签名） | `bundle.createUpdaterArtifacts: true` | ✅ 签名内容内联进清单后仍保留（下载页可核对） |
| `app-release.apk` | android job → `publish-extras` | ❌ |
| `latest.json` | `publish-updater-manifest` | — 清单本体 |
| `SHA256SUMS` | `publish-extras` | ❌ |

**`latest.json` 平台键映射（`tauri-plugin-updater` 查找顺序决定）**：插件先查 `{os}-{arch}-{installer}`（`nsis`/`msi`/`app`/`appimage`/`deb`），命中不到回落 `{os}-{arch}`。因此同一产物写两份键，覆盖不同安装方式的存量客户端：

| 平台键 | 指向资产 |
|---|---|
| `windows-x86_64` / `windows-x86_64-nsis` | NSIS `setup.exe`（MSI 安装的客户端走基础键回落） |
| `darwin-aarch64` / `darwin-aarch64-app` | `Orbit_aarch64.app.tar.gz` |
| `linux-x86_64` / `linux-x86_64-appimage` | `…amd64.AppImage.tar.gz` |
| `linux-x86_64-deb` | `…amd64.deb`（deb 安装的客户端走 `install_deb`） |

任一平台解析失败只告警跳过；**全部平台解析失败则拒绝发布空清单**（多为签名密钥不匹配或产物缺失）。

### 3.5 更新通知机制

- **口径：手动检查，不自动轮询**。本地优先应用的更新时机归用户掌控（决策同 qraft 与 07 #20）。因此「通知」由三处构成，而非后台弹窗：
  1. **关于与更新**（设置页分类）：`检查更新` → 发现新版本 → `下载并安装 X.Y.Z` → 重启（`tauri-plugin-updater` + `plugin-process`）；
  2. **关于 → 更新日志**：`src/lib/changelog.ts` 提供「我装的是哪版、这版有什么」，与仓库 `CHANGELOG.md` 同源双写；
  3. **Release 正文 + `latest.json.notes`**：未签名平台的放行指引（SmartScreen / Gatekeeper）与完整性校验方法，用户在应用内点开也能读到版本说明。
- **链路**：`plugins.updater.endpoints` → `https://github.com/mecoren/orbit/releases/latest/download/latest.json` → 比对 `version` → `download → verify(signature) → install → relaunch`。
- **失败口径**（必须在 UI 文案里保持诚实，ADR 0004 原则：不静默伪装已签名）：
  - 私钥未注入时期产物签名为空 → 应用内校验失败 → 提示「安装包未签名，可从 Release 页手动下载」（手动路径 + `SHA256SUMS` 不受影响）；
  - endpoint 不可达 → 提示网络/配置问题；
  - `latest.json` 不存在（Release 为草稿）→ 属流程事故，见 §7 排查表。

### 3.6 签名与密钥（三套，别混）

| 密钥 | 作用 | 存放 | 缺失后果 |
|---|---|---|---|
| Windows 代码签名证书 | Authenticode 消除 SmartScreen | `Secrets`（购证后启用） | 未签名：用户手动放行，`SHA256SUMS` 兜底 |
| macOS Developer ID + 公证 | Gatekeeper 放行 | `Secrets`（`APPLE_*`） | 未签名：`xattr -cr` 放行说明 |
| **updater minisign 密钥对** | 更新包签名校验（`createUpdaterArtifacts`） | 私钥进 `Secrets`，**公钥在 `tauri.conf.json` 的 `plugins.updater.pubkey`** | **构建直接失败**（刻意保护）；公钥私钥不配对 → 清单走空 → 拒绝发布 |
| Android release keystore | APK 签名（可上架） | `apps/mobile/android/key.properties`（gitignore） | 回落 debug 签名：可安装、不可上架 |

- **轮换**：updater 密钥轮换会使**已安装的旧版本拒绝升级**（`pubkey` 变更）。因此轮换必须「先发一版带新公钥的常规更新 → 确认装机率 → 再轮换私钥」，并接受一次「重新下载安装」的过渡通知；丢失私钥等价于强制全部用户重装（07 #50 记录）。
- **一次性配置清单（维护者）**：见 §6 首版验证。

## 四、参与角色与职责

| 角色 | 职责 | 边界 |
|---|---|---|
| **发布者（维护者本人）** | 决定发版范围 → `pnpm bump` → 写两份日志 → 跑 CI 等价检查 → `dry_run` 预演 → commit + tag push → 抽查 Release（清单可访问、资产 200、应用内检查更新通） | 唯一有权打 tag / 改密钥的人 |
| **CI（`release.yml`）** | 门禁校验、三平台构建、签名、单点合成清单、汇总哈希、附加资产 | 不做版本决策；版本号一律从清单读 |
| **`scripts/bump-version.mjs`** | 版本同步与一致性校验（`--check` 供 CI/本地复用） | 不提交、不打 tag（保持工作区交人确认） |
| **`ci.yml`（日常门禁）** | 每次 push/PR 保证可构建 + 单测 + e2e + FRB codegen 一致 | 不产出任何发布物 |
| **AI 编码工具（本仓库 agent）** | 收到「改版本号 / 升版本 / bump 到 X.Y.Z」请求时按 §3.1 → §3.2 全流程执行（脚本 + 双日志 + 守护测试），并明确告知尚未提交 | 不擅自 commit / tag / 推送；不代写 Release 正文 |

## 五、落地映射（文件 ↔ 职责）

| 文件 | 职责 | 何时改 |
|---|---|---|
| `scripts/bump-version.mjs` | 版本同步（升版 / `--check`） | 清单增删时 |

| `apps/desktop/src/pages/about-page.tsx` | 关于页（版本徽标 + 更新日志渲染） | UI 变化时 |
| `apps/desktop/src/test/release-consistency.test.ts` | 发版一致性护栏（版本/日志/日期） | 新增版本清单时 |

## 六、首次发布的验证清单（顺序不可换）

1. `Secrets` 配置 `TAURI_SIGNING_PRIVATE_KEY`（私钥内容）+ `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`；确认 `tauri.conf.json` 的 `plugins.updater.pubkey` 与私钥同源（配对失败会得到空 `latest.json`）；
2. 本地 `pnpm bump:check` → `VERSION_SYNC_OK`；`pnpm typecheck` + `pnpm test`（含新护栏 8 例）全绿；
3. Actions 手动跑 `release` 且 `dry_run=true`：确认三平台构建通过、`.sig` 已产出（artifact 或日志可见）；此时**不应**出现 Release；
4. 打 tag 正式发版；流水线四作业全绿；
5. 校验（任一台机器，无需登录）：
   ```bash
   curl -sI https://github.com/mecoren/orbit/releases/latest/download/latest.json   # 期望 200
   curl -s  https://github.com/mecoren/orbit/releases/latest/download/latest.json | jq '.version, (.platforms | keys)'
   ```
   逐条 `curl -I <platforms 里的 url>`，期望 200；
6. 应用内「设置 → 关于与更新 → 检查更新」端到端走一遍（发现 → 下载 → 安装 → 重启后版本号与关于页一致）；
7. 下载 `SHA256SUMS` 校验任一安装包哈希一致（确认清单不再是占位文本）。

**审计门禁转硬拦截的 promote 条件**：连续 2 次发版 `cargo audit` / `pnpm audit` 无高危且日志已沉淀基线口径后，去掉 `release.yml` audit job 中两个 `continue-on-error: true`（一行改动），并在 `docs/08` 本行记录日期。

## 七、异常处置

| 症状 | 定位 | 处置 |
|---|---|---|
| 应用内检查更新恒失败「签名校验失败」 | `latest.json` 的 `signature` 为空 / 与 `pubkey` 不配对 | 确认 `createUpdaterArtifacts` 与 Secret 就位后重跑 manifest 作业；已发布版本不可修补则发下一 patch |
| endpoint 404 | Release 是草稿，或 `latest.json` 未上传 | `gh release view <tag>` 查看 `isDraft`；manifest 作业末尾有兜底转公开发（重跑该作业即可） |
| 更新下载 404 | 清单 URL 与资产名不一致（有人手工改名/删资产） | 本仓库不做资产改名；恢复资产名后重跑 manifest 作业 |
| 只完成部分平台构建 | 矩阵某平台失败 | 修好后 `workflow_dispatch`（tag ref + `dry_run=false`）**重跑全链路**：作业幂等，`--clobber` 与临时名三步保证覆盖旧资产 |
| `SHA256SUMS` 内容为占位/缺 APK | `publish-extras` 未跑或产物未就绪 | 重跑 `publish-extras`（它会重新下载全部资产汇总） |
| 发错版本（含严重 bug） | — | ① 立刻发更高 patch（**`latest.json` 只升不降**，回填低版本清单对已升级用户无效）；② 严重时把该 Release 标 `prerelease` 并在 Release 正文顶部加醒目告警；③ 极端情况删除 Release 与 tag（已下载用户不受影响，务必在仓库 Issue/Release 说明处置） |
| 需要撤销公开 | `gh release delete <tag> --cleanup-tag` | 仅限发布事故，删除后必须补发修好的版本，否则存量客户端检查更新会 404 |

## 八、明确不做的取舍

- **不做资产改名规范化**：无多命名需求（qraft 的 `release-asset-map.sh` 是为解决自身改名后 URL 对齐问题）；
- **不做自动更新轮询 / 后台弹窗**：本地优先，更新时机归用户（口径同 07 #20）；
- **不做 canary / 灰度双清单**：单渠道发布，M6+ 再评估；
- **不扩平台矩阵**（Windows arm64 / macOS x64 / Linux arm64）：按真实用户分布评估，属成本决策；
- **不引入 SBOM / 更重的供应链工具链**：先让审计基线跑两版再评估（qraft 的 SBOM 作业本仓库暂不跟进）；
- **遗留（已入 `docs/07` #50）**：应用内更新的**安装方式识别**（MSI/NSIS/便携/dmg）与**不支持就地升级时兜底跳转 Release 页**——qraft 在 Rust 侧有 `resolve_package_type` / `detect_windows_install_kind` 一整套纯函数可作移植蓝本，本批不动（属功能增强而非流程问题）。
