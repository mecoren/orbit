## 一、总体结论

同步体系的**核心算法层质量较高**：LWW + version 平局裁决、墓碑时间戳保留、复活裁决、KeyMismatch/CryptoLocked 语义区分、write_atomic 文件协议、uuid 唯一索引、引擎 try_lock 防重入等，注释考古显示经历过 Fix-01~Fix-13 多轮真实故障修复，单机单云 happy path 可靠。

但系统性排查发现 **10 个高危（P0）、约 20 个中危（P1）问题**，集中在四类：

1. **S3 链路处于"最小可用"状态**：无分页（>1000 对象静默截断）、阿里云 OSS 签名必 403（service 名硬编码）、前缀污染、元数据恒 0，且 S3 链路零测试。
2. **WebDAV 链路有一处贯穿性解析缺陷**：PROPFIND 不识别标准 `resourcetype`，目录条目混入文件列表且 name 退化为整条 URL，向下引发附件每轮失败、KeyMismatch 守卫失效两个高危连锁。
3. **协议适配层未归一化**：S3 与 WebDAV 在"列举完整性、name 语义、元数据、错误分类、重试覆盖"五个维度存在真实偏差，而协议无关引擎层对这些差异无感知，其中一处（`cloud_has_module_data`）已实际踩坑。
4. **可观测性为零**：日常增量同步完全不写 `sync_history`，"上次同步成功了吗、为什么失败、耗时多少"当前无法回答——99.9% 成功率目标没有度量基础。

**核心结论**：数据安全类 P0 问题（共 8 项涉及数据丢失/污染风险）修复前，WebDAV 多设备 + 附件场景、阿里云 OSS 场景、S3 大桶场景、删库重装场景均存在不可逆数据风险；修复后配合三层重试体系，99.9% 成功率目标可达（论证见第十节）。

## 三、高危问题（P0：数据丢失 / 污染 / 功能不可用）

> 每项格式：位置 → 问题 → 触发场景 → 修复方向。严重度按"最坏后果"排。

### P0-1 ✅已修复 WebDAV PROPFIND 不识别标准 `resourcetype`，目录条目污染文件列表

- **位置**：`webdav_adapter.rs:336-342, 541-547`（PROPFIND body 仅请求 `getcontentlength`/`getlastmodified`）；`webdav/propfind.rs:61-63`（唯一能置 `is_collection` 的分支只认微软私有 `<iscollection>1</iscollection>`）
- **问题**：RFC 4918 标准的 `<D:resourcetype><D:collection/></D:resourcetype>` 是空元素对，不产生文本，落入 `_ => {}` 分支——`is_collection` 在坚果云/Nextcloud/群晖/wsgidav 等所有主流服务器上**恒为 false**，`webdav_adapter.rs:391, 592` 的目录过滤形同虚设。
- **连锁**：目录条目（href 以 `/` 结尾）经 `webdav_adapter.rs:400-407` 的 basename 提取得到空串，回退为**整条 URL 当文件名**混入 `list_all_files` 结果 → `BasePathAdapter::list_assets`（`cloud_sync_api.rs:121-126`）把该垃圾项收进 `cloud_hashes` → 附件 pull 的 `to_download` 差集每轮都含它 → `download_asset(整条URL)` 必 404 报错且**永不收敛**。
- **影响**：WebDAV + 云端有附件的设备，每轮同步的附件阶段持续报错，真实错误被淹没。
- **修复方向**：PROPFIND body 增加 `<d:resourcetype/>`；解析器在 Start 事件识别 `collection` 子元素置位；同步过滤尾斜杠 href。一个点修三处。

### P0-2 ✅已修复 KeyMismatch 防污染守卫在 WebDAV 下完全失效

- **位置**：`cloud_sync/engine.rs:929-961`（`cloud_has_module_data`/`is_module_data_path`）；根因同 P0-1 + `webdav_adapter.rs:333`（Depth:1 只列一级）+ `:411`（name=basename）
- **问题**：守卫依赖 `list_files(base_path)` 返回 `modules/{name}/data.waitsync` 形态路径。WebDAV 下 list 只返回 base 一级子项且 name 是 basename，`is_module_data_path` 要求路径含 "modules" 段且以 `/data.waitsync` 结尾——**恒 false**。因此 `decide_auto_upload_behavior` 的 Block 分支在 WebDAV 上永不触发：当云端已有 Key A 加密的模块数据但缺 `crypto/config`、本地持有 Key B 时，会把本地 Key B 的 crypto/config **自动上传覆盖**，随后探针报 KeyMismatch 终止本次同步，但云端密钥配置已被污染，**全部设备从此 KeyMismatch**。S3 路径行为正确（list_objects 返回相对全路径），恰好掩盖了 WebDAV 侧破损——典型的"跨模块偏差已实际踩坑"。
- **修复方向**：`cloud_has_module_data` 不再依赖 `list_files` 契约，改为对 `{base}/modules/todos/data.waitsync` 做一次 404 探测（下载 1 字节或 HEAD）；并补 basename 形态回归用例。

### P0-3 ✅已修复 S3 ListObjectsV2 无分页，超 1000 对象静默截断

- **位置**：`s3_adapter.rs:163-199`（`list_all_files`）、`:296-327`（`list_assets`）；`s3/list_objects.rs` 只提取 `Key`
- **问题**：不传 `max-keys`、不读 `IsTruncated`/`NextContinuationToken`、无循环（全仓 grep 确认零出现）。S3 单页默认 1000 条：附件超过 1000 后，pull 永远拉不到第 1001 个附件、push 把云端实际存在的附件判为不存在而全量重传；`cloud_has_module_data` 探测结果失真。
- **对比**：WebDAV PROPFIND Depth:1 一次返回全部（多数服务器无分页），不受影响——两个适配器在"列举完整性"上方向相反。
- **修复方向**：循环携带 `continuation-token` 直到 `IsTruncated=false`；顺带提取响应中已有的 `<Size>`/`<LastModified>`（见 P1-9）。

### P0-4 ✅已修复 阿里云 OSS 签名 service 名硬编码，OSS 用户全部 403

- **位置**：`s3_adapter.rs:104-139`（string_to_sign 与 signing_key 两处硬编码 `"s3"`）；`s3/url.rs:60-67` 的 `infer_service()`（OSS 域名应返回 `"oss"`）为**死代码**，写了没接
- **问题**：阿里云 OSS 的 V4 签名 credential scope 要求 `{date}/{region}/oss/aws4_request`，硬编码 `s3` 导致 OSS 默认域名下所有请求 403，功能完全不可用，且错误信息是裸 XML 无法自助定位。
- **修复方向**：`infer_service` 接入签名链（一行改动解锁 OSS 用户）；region 空值校验（`engine.rs:73-93` 的 `validate_config` 不查 region，漏填 region 同样全 403）。

### P0-5 ✅已修复 删库重初始化 + 残留 `sync_state.json` → 云端被空数据覆盖

- **位置**：`cloud_sync/push.rs:245-260`（`should_skip_push`）；`state.rs:92-94`（state 文件与 DB 文件分离存放）
- **问题**：项目迁移史（0002-0004 并回 0001）要求存量库**删库重初始化**。若用户删了 DB 文件但保留 `sync_state.json`（两者在不同路径，删库不会带上）：state 里 `remote_fp` 与云端一致 → Pull 全模块 Skip（`pull.rs:235-240`），空库拉不回任何数据；Push 侧 `prev_state` 存在、本地空指纹 ≠ state.fp → 不跳过 → **上传空 items + 空墓碑覆盖云端**。Fix Issue-2 的空数据守卫只覆盖 `prev_state.is_none()` 分支，此场景失效。
- **修复方向**：push 前校验"local_items 为空但 state.count > 0"时阻断并要求强制确认；或删库场景提供清理 state 的引导。

### P0-6 ✅已修复 Pull 单模块失败后继续 Push：陈旧数据覆盖云端新数据

- **位置**：`pull.rs:196-198`（Failed 只进 errors 不更新 state）；`push.rs:332-349`（reconcile 见 fp 不一致即清空 remote_fp 触发重传）
- **问题**：设备 B 推了模块 X 新数据后，设备 A pull 时 X 下载失败（网络抖动）→ A 的 state.remote_fp 仍是旧值 → 同一轮 sync_now 继续 push → reconcile 发现不一致 → **A 用陈旧本地数据重传 X 覆盖 B 的新数据**。B 若不再同步则数据永久丢失。
- **修复方向**：本轮 pull 产生 Failed 的模块，push/reconcile 对其跳过（把失败模块集传入 push_all）。

### P0-7 ✅已修复 `data.waitsync` 与 `meta.waitsync` 两段上传无原子性（删除丢失窗口）

- **位置**：`push.rs:193`（先传 data）与 `:212`（后传 meta），墓碑只存于 meta
- **问题**：两 upload 之间崩溃/断网 → 远端新 data（不含新删的存活行）+ 旧 meta（缺新墓碑）→ 其他设备 pull 时既不应用删除、data 里又没有该行 → **已删记录在云端视角"复活存活"**，回收站语义被破坏。
- **修复方向**：单容器合并（data+meta 同包）属格式演进；短期可先传 meta（带墓碑）后传 data，使中断窗口最多"多删不漏删"，配合 reconcile 兜底。

### P0-8 ✅已修复 附件 pull 每轮全量重下 + 落盘非原子

- **位置**：`attachments.rs:259-262`（`tokio::fs::write` 直接覆盖）；`attachment_repo.rs:62-69`（`mark_local_cached` 仅 UPDATE，不 INSERT）；`db/sync_registry.rs:8-17`（`sys_attachments` 不在 SYNCABLE_TABLES）
- **问题**：① 新设备/删库后 `sys_attachments` 无记录 → 差集（云端有-本地有）永不为空 → **每轮同步把云端全部附件重新下载一遍**，在坚果云限流下是持续流量负担；② 下载中途崩溃留半截文件，但文件名即 hash（内容寻址），损坏内容被"哈希背书"；③ 解密后不校验 sha256 与文件名一致。
- **修复方向**：`sys_attachments` 纳入同步白名单（或 pull 后 upsert 记录）；落盘改用已有的 `fs_util::write_atomic`；下载后校验 hash。注意 todos 模块当前 `has_attachments: false`（`modules.rs:53`），实际负载低，但代码是通用路径，开启附件功能前必须修。

### P0-9 ✅已修复 merge 的 `_table` 路由无白名单校验

- **位置**：`merge.rs:113-119`（`item["_table"]` 未校验直接作表名路由）；`generic_repo.rs:854-859`（只验标识符合法性不验白名单）
- **问题**：远端 data.waitsync 中的 `_table` 可指向任意本地表（`sync_configs`、`cfg_kv`、`sys_attachments` 等），merge 会加载该表列元数据并 INSERT/UPDATE——**越过同步白名单写非同步表**（凭据、配置）。前提是 Data Key 泄露或云端数据被篡改，但同步层作为防线不应缺席。读取侧（db_loader.rs:41-44）已做白名单，写入侧漏了。
- **修复方向**：`items_by_table` 的 key 必须 ∈ `module_def.tables`（一处 if 即可对齐读写两侧标准）。

### P0-10 ✅已修复 S3 prefix 前缀污染：base_path 是其他目录前缀时跨目录列出

- **位置**：`s3_adapter.rs:171`（query `prefix=base_path` 不带尾斜杠）；`list_objects.rs:18-22`（剥离按 `{prefix}/` 带尾斜杠）
- **问题**：S3 prefix 是字符串前缀匹配：`prefix=wait` 会同时列出 `wait2/...`、`waitfoo/...` 的对象；解析端因 key 不以 `wait/` 开头保留全名——返回了本不该出现的 key 且名字形态不一致，`cloud_has_module_data` 探测与 push/pull 去重失真，多用户共享 bucket 场景数据串目录。
- **修复方向**：query 的 prefix 改为 `prefix_with_slash`（与解析端口径对齐，一行修复）。

## 六、归一化差距矩阵（S3 vs WebDAV 逐维度对照）

这是"消除模块间功能偏差与逻辑不一致"的核心对照表。**协议无关引擎层假设了统一契约，但两个适配器在五处真实偏离，其中两处已被引擎踩坑（P0-2、P1-8）**。

### 6.1 数据处理逻辑

| 维度 | S3 | WebDAV | 偏差后果 |
|---|---|---|---|
| 列举完整性 | 无分页，>1000 截断（P0-3） | Depth:1 单请求全量（多数服务器） | S3 大桶漏文件 |
| `RemoteFile.name` 语义 | 相对 base 的**完整 key 路径**（`modules/todos/data.waitsync`） | **basename**（`data.waitsync`） | 引擎 `is_module_data_path` 只认 S3 形态 → WebDAV 下守卫失效（P0-2）；traits.rs 无契约文档 |
| size/last_modified | 恒 0（响应有值未提取） | 真实值 | 备份列表排序 S3 下失效（P1-8） |
| href/key 编码 | 隐式依赖 url crate | href percent-encoded 不解码、build_url 纯拼接 | 靠巧合兜底，`#`/`?`/裸 `%` 即错位 |
| 内容校验 | 无 ETag/Content-Length 校验（GCM 标签兜底但报错形态误导） | 同左 | 损坏表现为"解密失败"误导诊断 |
| etag/If-Match | 无 | 无 | 一致地没有（版本比较全靠包内指纹） |

### 6.2 同步策略

| 维度 | S3 | WebDAV | 偏差后果 |
|---|---|---|---|
| HTTP 级重试（100/200/400ms ×3） | 仅 GET/PUT | 仅 GET/PUT | 一致地缺：DELETE/HEAD/PROPFIND/MKCOL 裸奔 |
| 业务级重试（2/4/8s 或限流 30/60/120s ×3） | 仅 pull_all/push_all 包裹 | 同左 | 附件同步两侧都在保护外（P1-23） |
| 目录创建 | 无（扁平 key） | MKCOL 递归 + 405 容忍 + 409 递归 + 5xx 幂等复查（工程精细） | 语义天然对齐；但 WebDAV 首目录首文件 2N+1 请求开销 |
| 并发控制 | 附件 4 路（无速率感知） | 同左 | 坚果云限流冲突 |
| 超时 | 30s 总超时（0→30 映射已做，两适配器一致） | 同左 | 一致；大附件两侧同病（P1-22） |

### 6.3 错误处理（同一状态码在两适配器/两方法上的分类矩阵）

| 状态码 | GET/PUT（统一路径 `from_http_status`） | PROPFIND/MKCOL/DELETE/HEAD（手写路径） | 结论 |
|---|---|---|---|
| 401/403 | → `Auth` | → `Network`（PROPFIND/MKCOL）；DELETE 提示语含权限但类型仍 Network；HEAD 一律 false（P1-2） | **同 crate 两套标准** |
| 404 | → `NotFound`（类型化） | PROPFIND → 静默空列表（endpoint 配错被掩盖）；HEAD → false | 双偏差 |
| 409 | — | GET 靠字符串嗅探翻译（P1-6）；MKCOL 递归建父（好）；DELETE 提示不准 | WebDAV 内部三种口径 |
| 5xx | retryable:true + HTTP 短重试（限流文本除外） | PROPFIND retryable:false + body 丢弃（P1-1）；MKCOL 有幂等复查（好） | 退避行为分裂 |
| 429/限流 | 文本匹配（识别不出 S3 SlowDown，P1-3） | body 丢失后匹配必然失败 | 限流场景全链条脆弱 |

### 6.4 附件路径语义（.waitsync 迁移未收口）

适配器自身实现了 `.waitsync` 新路径族（upload/download 双读回退、list 剥后缀），但生产链路全部经 `BasePathAdapter`，后者把 asset 方法族重写为**无后缀 legacy**（`assets/{hash}`，单读无回退，list 不剥后缀）——两套语义并存（P1-7）：适配器实现是死代码，`list_assets` 返回的 `.waitsync` 后缀名与裸 hash 永不相等导致判存失效。

### 6.5 归一化目标态（建议的统一契约）

1. `RemoteFile.name` 定义为"相对 base_path 的标准路径"（S3 现行为），WebDAV 通过拼接目录上下文对齐；`traits.rs` 补契约文档与字段有效性说明。
2. 所有 HTTP 方法（GET/PUT/DELETE/HEAD/PROPFIND/MKCOL）统一经 `from_http_status` 分类（带 body），`retryable` 单一来源。
3. 适配器补齐两个统一原语：`exists(path) -> Result<bool>`（区分 404 与错误）与 `stat` 元数据（size/last_modified 必填，填充不了须显式 None 而非 0）。
4. asset 方法族只允许一条路径语义（BasePathAdapter 透传或删除适配器死代码）。
5. `list_all_files` 默认实现改为"未实现即报错"而非静默空（fail-fast，防 P1-9）。

## 九、同步成功率监控机制设计（目标 ≥99.9%）

### 9.1 现状

`sync_history` 表（`models/business.rs:395-405`：sync_type/status/started_at/finished_at/pulled_count/pushed_count/conflict_count/error_message）与 repo（insert/update_status/get_recent/get_last_successful/delete_old）**已就绪但增量同步零接线**——唯一写入方是全量备份。这是 99.9% 目标的第一阻塞项：**无度量则无管理**。

### 9.2 设计方案（分五层，均为后续实施项，本次不改代码）

**第一层：记录接线（基础）**
- `SyncEngine` 三入口（sync_now / push_only / pull_then_push）在 `acquire_lock` 成功后 insert `running`，终态 update：`success` / `failed` / `skipped`（防重入跳过单列，不计入成功率分母）/ `partial`（主流程完成但 errors 非空）。
- status 建议由自由字符串收敛为枚举约束（当前 "running"/"success"/"failed"/"cancelled" 无校验）。

**第二层：错误码标准化**
- 新增 `error_code` 列，取值直接复用已有的 `CloudSyncError::category_tag()`（`[network]`/`[auth]`/`[key_mismatch]`/`[password]`/`[config]`/`[database]`/`[adapter]`…）——分类体系已存在且经回归测试，只差落库。
- 同步类型细分：`incremental_pull_push` / `push_only` / `startup_pull_push`，与现有 `cloud_full_backup` / `local_full_backup` 并列。

**第三层：阶段化成功口径（99.9% 的分母/分子定义）**
- 核心同步场景定义为三个：① 手动全流程；② 定时全流程；③ on-change push_only。
- 单轮成功标准：Data Key 对账 → pull 合并 → push → 附件 pull/push 全链路无 `failed` 且 `errors` 为空；`partial` 不算成功。
- 成功率 = success / (success + failed + partial)，按周窗口滚动统计；`skipped` 不进分母。
- 每阶段耗时（data_key/pull/push/att_pull/att_push）建议以已有 `SyncProgress` phase 事件为源记入 started/finished 差值，便于定位慢点。

**第四层：验收与告警**
- **本地验收口径（不上传遥测，符合 PRIVACY 承诺）**：测试环境跑 1000 轮双实例自动同步（A/B 交替编辑-收敛），统计成功率 ≥ 999/1000。可在 m4 e2e 基础上参数化轮次构建 "m5 同步成功率基准测试"。
- 应用内展示：设置页"最近同步记录"列表 + 30 天成功率（`get_recent_by_types` 已有，差 UI 接线——注意其文档自认"功能开发中"）。
- 告警规则：连续 3 次 failed → sync-indicator 常驻红点；key_mismatch 已有专门事件与恢复页闭环（保留）。

**第五层：99.9% 可达性论证**
- 随机网络失败：现有三层重试（HTTP 级 4 次 + 业务级 3 次指数退避）下，单请求残余失败概率 p^12 量级，远低于 0.1%——**重试体系本身足以支撑 99.9%**。
- 系统性失败源（当前实际拉低成功率的）全是本报告的可修复缺陷：附件垃圾条目每轮 404（P0-1）、OSS 403（P0-4）、坚果云限流短退避（P1-1/P1-23）、大附件 30s 超时（P1-22）、push 中止连带附件跳过（P1-11）等。
- 结论：**完成 P0 + P1 修复并接线第一~三层监控后，99.9% 目标可达且可验证**；未修复前该目标无意义（存在每轮必失败的场景）。
