## 八、问题与建议

1. **`version` 跨端不一致（建议修或明确验收口径）**：软删发起端 `version=2`、pull 合并端 `version=1`。`version` 参与 LWW 同毫秒比较，虽然业务数据完全一致、后续更新会各自递增，但严格逐字段口径必报差异。建议二选一：引擎在 pull 合并时传播远端 `version`；或在一致性验收规范中显式剔除 `version` 等本地同步元数据。
2. **`sync_conflicts` 只在裁决端留档**：属既定语义（本地审计表不进白名单），验收口径应显式排除，避免误判为数据不一致。
3. **验收字段 `downloaded_chunks` 不存在**：`SyncState` 顶层键为 `last_synced_at / last_pulled_at / last_synced_clock_ms / last_pushed_clock_ms / device_id / manifest_epoch / remote_tables / remote_tombstones / undeletable_chunks`，没有 `downloaded_chunks`。建议补计数或修订验收文档；本轮零流量口径用「`manifest_epoch` 不变 + 桶指纹不变 + `pulled_modules`/`downloaded_attachments` 计数 + 前后账本比对」替代。
4. **幂等同步仍有 40–50 s 固定开销**：移动2 零流量二次同步 39,786 ms、桌面 46,296 ms，而实际传输为 0。耗时集中在远端列举与 11 表桶指纹校验（523–524 个桶 + 258 个附件 HEAD/清单）。建议评估按 manifest 单文件短路、或对未变桶跳过二次校验，并补 10k/50k 档 profile 基线。
5. **移动端全量 pull 明显快于 push**（49,895 ms vs 91,469 ms）：push 侧含 258 附件上传与 523 桶写入，属预期，但建议在报告口径里把「附件占比」单列，便于跨轮对比。
6. **GUI 文案刷新滞后**：3.1 同步完成后页面仍显示「从未同步」，约 20 s 后才刷新为「上次同步：2026-11-15 …」。功能无影响，属可感知的观感问题，建议同步完成后主动失效该查询。
7. **移动端同步密码不缓存**：`force-stop`/重启即回「已锁定」，自动化必须先解锁再同步，否则同步会被静默跳过。建议把「解锁 → 回到设置页 → 点立即同步」固化进 E2E 工具（本轮已落 `sync_mobile2.py`：解锁后自动退回设置页，完成判据改为 UI 轮询「取消同步消失且立即同步重现」，不再依赖 `sync_state.json` 的中间写入）。
8. **`adb shell run-as cat` 会损坏二进制库**：抓库必须用 `adb exec-out run-as … cat`（不经 shell 的 CRLF 转换），否则得到 `database disk image is malformed`。
9. **移动2 序列号漂移**：需求写 `127.0.0.1:16416`，本轮该端口恒 offline（`adb kill-server`/`disconnect`/`reconnect offline` 均无效），改用同机第二模拟器在线序列号 `127.0.0.1:5557`。设备型号（SM-S9110）与应用版本（0.1.0+6）与需求一致，建议需求侧改为「按在线序列号取第二台模拟器」。

## 十、结论

**一致（阶段 3 与阶段 4 的三端业务数据）。** 证据：`verification_s3-p4.json` 的 `all_pass=true` —— 11 表 `table_counts` 在 `exclude_deleted` true/false 双口径下三端全等（false 口径合计 214,111 行，true 口径 `todo_tasks` 39,201 行即 799 墓碑）、11 表规范化摘要与首尾各 50 + 随机 100 抽样全等、`stats_aggregate(1999/2005/2018/2026)` 四年全等、258 附件（20,840,448 B）sha256 集合全等且含 2 个 8.5 MiB、回收站 799 行与 `deleted_at` 合计 1,433,965,318,447,312 全等、云端视图 `manifest_epoch=4` / 524 桶 / `remote_tables_sha256=21096accca96…` / `remote_tombstones_sha256=10fb5e68b609…` 全等；`cross-end-s3.json` 的 `m2_看到桌面变更=true` 与 `回流成功=true`（桌面改标题 + 新建项目 → 移动2 可见 → 移动2 改回 → 桌面可见，LWW 按 `updated_at` 大者胜）；阶段 3 时序 91,469 / 49,895 / 39,786 / 85,535 / 46,296 ms 与零流量幂等；阶段 5 四项（LWW 冲突桌面胜且三端各 1 行、`sync_conflicts` 1 行、墓碑传播不复活、错密报 `wrong_password` 不清数据、取消后 33,250 ms 回待命并可续跑成功）全部通过。

**不一致（严格逐字段口径，2 处本地元数据/本地审计表差异）。** 证据：阶段 5② 后 `todo_projects` 软删行 `uuid=d7d6fa1d-aeb1-4ffa-813d-7d2061644cfd` 的 `version` 为移动1=2 / 移动2=1（业务字段 `is_deleted`、`deleted_at=1794704339086`、`title`、`updated_at` 两端完全相同）；`sync_conflicts` 行数为移动1=0 / 移动2=0 / 桌面=1（该表不进同步白名单，只在裁决端留档）。差异清单与归因见第六节 6.2，修复建议见第八节 1/2。**剔除 `version` 与本地审计表后，三端业务数据、云端账本、附件与统计全部相等。**
