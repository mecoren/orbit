# ADR 0005 — 回收站：purge 与墓碑同步协议的边界

- **状态**：已采纳（Accepted）
- **日期**：2026-09-06
- **关联**：03 文档 §六（同步白名单/墓碑语义）、07 报告 §三 对比表「撤销/回收站」；实施为 orbit-core `api/trash_api.rs` + 桌面 `trash_cmd`/`trash_scheduler` + 移动端 FRB `api/trash.rs`

## 一、背景

删除的待办要能从回收站恢复（用户需求），对标 Todoist / 微软 To Do（30 天保留）/ Vikunja（可恢复 + 手动清空）。现状基础异常有利：

- 8 张 todo 表删除即软删（`is_deleted=1, deleted_at=now, version+1`），墓碑行始终在库；
- 云同步（无中心 server，S3/WebDAV 直连）以墓碑集为「删除」的唯一载体：
  - **Push**：`is_deleted=1` 行不上传 data 文件，仅以 `{uuid, deleted_at}` 进 meta 墓碑集（无上限）；
  - **Pull 合并**：item 级 LWW；本地为墓碑时走「复活裁决」——远端存活行的
    `updated_at ≥ 本地 deleted_at` 才复活（`merge.rs`），杜绝 uuid 重复行；
  - **墓碑应用**：远端墓碑 `deleted_at ≥ 本地 updated_at` 才本地软删（编辑胜删除）。

因此**恢复零成本**：`is_deleted=0` + `updated_at` 提升后，正常 push 存活行即可让对端
pull 时复活裁决自动传播恢复，同步引擎零改动。真正的设计难点只有一个：**物理删除
（purge）与墓碑协议的冲突**。

## 二、冲突：purge 制造的复活窗口

回收站需要两类物理删除：

1. **用户主动彻底删除 / 清空回收站**；
2. **TTL 自动过期清理**（保留档位 7/30/90 天，默认 30）。

物理删除把墓碑行从库里抹掉后，**本端 push 不再上传该 uuid 的墓碑**。若删除从未成功
push 到云端（或云端仍是删除前的旧存活数据），其他设备 pull 时会把旧存活版本
INSERT 回来——任务「复活」，用户明明已彻底删除。这是墓碑无 GC 的去中心化同步
（03 文档「墓碑不再有上限」）与回收站 TTL 的固有张力。

## 三、决策

### 3.1 手动彻底删除：无守卫，直接物理删

用户明确意图（二次确认 destructive 弹窗）优先于理论上的复活窗口。理由：

- 手动 purge 是显式动作，用户在该设备上看得见结果；即使极端场景下另一台离线已久的
  设备 pull 回旧数据，也是「旧设备同步滞后」这一已知语义（LWW 同上）；
- 给手动操作加守卫（「该删除尚未同步，无法彻底删除」）会让主流程不可用，收益不成比例。

### 3.2 TTL 自动清理：同步守卫

`maybe_purge_expired` 只清「已确认上传云端」的墓碑：

- 启用云同步（`sync_configs` 存在激活配置）时，仅清
  `deleted_at < last_synced_at` 的行——早于该时间点的删除已随成功 push 上传墓碑集；
- 从未成功 push（`last_synced_at=0`）→ 全部守卫跳过；
- 未启用云同步 → 无守卫直接清（没有其他设备可复活，云端也无数据）。

`last_synced_at` 取 `sync_configs`（每次成功 push/sync 后由两端 `run_sync` /
`sync_scheduler` 记账），而非 `sync_state.json` 的模块级 `pushed_at`：前者是 SQL
一次查询、DB 权威；后者需读文件且按模块粒度，对「todos 模块整体已推」的判定更绕。

守卫粒度说明：`last_synced_at` 记录的是**最近一次**成功同步，理论上「删除 → push →
又发生更多未 push 的删除」时，较早删除仍可清、较晚的会被正确挡住——每轮 tick 重新
判定，随下次成功 push 逐步放行，无积压风险。

### 3.3 每日一次记账，两端只做 tick 壳

`should_purge_now`（上次清理 ≥ 24h 前）+ `cfg_kv: trash_last_purge_ms` 记账。
判定逻辑单一实现在 orbit-core；两端守护只负责 60s tick + 启动首轮：

- **桌面**：`trash_scheduler`（tauri::async_runtime 常驻，lib.rs setup 启动）；
- **移动端**：FRB `start_trash_scheduler`（BootGate 在 DB 就绪后启动；进程可被杀，
  只能惰性清理——应用运行时 tick + 启动补清，与 holiday scheduler 同模式，
  依赖 ADR 0002 的「手机被杀后无 Dart 进程」结论）。

### 3.4 保留档位：cfg_kv 本地偏好，不进同步白名单

`trash_retention_days`（档位 7/30/90/0=永久，默认 30）存 `cfg_kv`（migration 0003
本地 KV 表）。与 `holiday_fixed_hour` 同边界：各端各自设置，不随云同步——保留策略
是本机行为偏好；TTL 清理本身受 3.2 守卫约束，各端不同档位最终收敛一致
（早清的端也没清掉未同步墓碑，晚清的端补齐），无一致性风险。

### 3.5 恢复与子行：不级联

软删任务时子任务/评论/提醒**不级联软删**（现状），恢复任务后它们自然回归
（查询侧按 task_id 关联）；仅 purge 时物理级联清除，避免孤儿行。

## 四、被否决的替代方案

- **墓碑 GC（全端一致清）**：需要全设备握手（谁知道几台设备？），无中心 server
  的去中心化架构下不可实现，维持 03 文档「墓碑无上限」现状。
- **purge 后回写墓碑**：物理删除后保留 uuid 占位行——等于没删，墓碑行数只增不减。
- **只做手动 purge、不做 TTL**：违背需求「保留时间可配」；且长期不清理的墓碑行
  会缓慢累积（每行全字段），TTL 是数据卫生刚需。
- **同步层专用 purge 协议（云端墓碑集清理指令）**：需扩展 meta 格式 + 两端版本
  兼容，成本远超收益；守卫方案在「最坏情况 = 任务晚几天才彻底消失」的代价下已足够。

## 五、后果

- 已彻底删除的任务在「其他长期离线设备」上理论上可能因拉取旧存活数据而短暂复活
  → 属去中心化 LWW 的既有语义（编辑同理），文档明示即可；
- TTL 清理的滞后（最多 = 距上次成功 push 的间隔 + 24h 记账粒度）为可接受代价；
- `trash_retention_days` 各端独立，设置页文案已明示「本机设置，不随云同步」。
