## 一、总体结论

1. **P0 静默失效集中在「包装器与 trait 默认实现」的组合空隙**：`BasePathAdapter` 少转发 `download_with_token`/`upload_conditional`/`exists` 三个方法（F22），落到 trait 的 mock 友好退化默认——令牌恒 `None`、前置条件被丢弃、HEAD 降级为整对象下载。生产链路只经包装器，故 S3/WebDAV 的**清单 CAS 从未在网络上发出过条件头**，且单测因 mock（实现了真方法）强于生产而长期假绿。同根因另有 F23：包装器先拼 `base_path`，而分片协议判定要求 `path.starts_with("assets/")` → WebDAV 大附件分片协议自落地起从未执行。
2. **数据丢失面：回收站物理清理守卫线被非干净轮次推进**（F24）：手动同步在 `Ok(SyncResult)` 时无条件推进 `sync_configs.last_synced_at`，含 `skipped` 与 `errors` 非空（部分表失败只进 errors 不外抛）——未推送的墓碑可被提前物理删除，对端 pull 复活已删任务。现已把记账收口到引擎漏斗的唯一回写点（`SyncResult::advances_ledger()`）。
3. **测试设施自身是风险源**（F25/假服务）：唯一端到端用例探不到本机 WebDAV 即 panic（干净机器必红），且预清理停在老布局、从不删现布局对象。本轮建成零依赖故障注入假服务（`tests/common/mod.rs`）与稳定性矩阵（`tests/sync_fault_matrix.rs`，10 用例），并让 m4 用例降级为 `#[ignore]` 的真服务端方言用例。
4. **协议合规小修一批**（F26-F32）：PROPFIND 补 `<getetag/>`（列举侧并发令牌）、S3 列举补 `Size`/`LastModified`（备份列表倒序在 S3 上恒失效）、multipart 失败补 Abort、Complete 体转义服务端 ETag、href 百分号解码（中文备件名乱码）、207 内层 status 取舍、typed error 去串嗅探 + trait 文档写明两协议列举深度差异。
5. **安全两处收口**（F33/F34）：KDF 迭代下限 guard 挂三入口（云端 bundle / 本地 meta / 备份文件头，下限取历史最小值 200k）；错误串脱敏 `brief()`（截 200 字符 + 丢含 `Authorization`/`Credential`/`<StringToSign>` 的行）挂全部 5 个 `from_http_status` arm——这是 `config_enc/storage.rs` 注释里一直声称存在、此前全仓无实现的「日志脱敏红线」。
6. **ADR 0010 第一拍落地**（F43-F46）：版本门禁 `!=`→`<`、独立错误码 `PayloadVersionMismatch`、`DeviceCheckpoint.app_version` 协商位、AAD 绑定代码入库但写侧门控默认关闭（第二拍需先发 0.2.0 并让全网设备升级）。
7. **性能：A10「同步字节复用」主体落地**（F40/F41），F42 精确失效补齐。F41 的实现过程中发现并修正了方案原型的一个真实缺陷：**pull 的冲突判据水位线不能复用为 push 的脏判据**（pull 结束会把它推到本轮编辑之后），现以独立字段 `SyncState.last_pushed_clock_ms` 承载（见 §四.3）。

## 四、本轮补充发现与设计修正

1. **假服务必须支持 keep-alive**（F25 后续）：原 `handle_conn` 一请求一响应且恒 `Connection: close`，与 reqwest 连接池存在「服务端已关闭 vs 客户端复用」竞态——9MiB 分片上传用例偶发 `PROPFIND … error sending request`（且每请求一条新连接把用例拖到分钟级）。改为同连接请求循环（半截体/停滞响应后主动关闭）后 10/10 稳定通过。
2. **测试 fixture 必须走逻辑时钟**：故障矩阵/`m4` 原用手写 `updated_at = 1/2` 或裸墙钟。F41 的水位线与行 `updated_at` 同域比较（都来自 `db::clock`），fixture 改为 `clock::next_ms()` 才既贴近生产写路径、又避免同毫秒 flaky。
3. **F41 水位线不能复用 `last_synced_clock_ms`**（方案原型修正）：pull 结束会把它推进到「本轮结束时刻」；`pull_then_push` 场景下 push 复用它会把**本轮开始前的本地编辑**判成非脏 → 编辑永不上传（故障矩阵 `four_ops_converge` 曾据此翻红，两个协议一致复现）。现以独立字段 `last_pushed_clock_ms` 承载 push 水位线（只由 push 成功推进，且推进到 **push 开始**时的时钟快照，本轮开始后的新写入留给下轮），pull 的冲突判据语义零改动。
4. **行数比对是时间戳判据的必要补集**：merge 应用远端墓碑时本地软删行的时间戳被锚定为墓碑原始 `deleted_at`（可能早于水位线，Fix-02 明确不得漂移），纯时间戳判据对「桶内活行减少」是盲的。`LocalBucketScan` 以「存活行数 ≠ 远端 `ChunkRef.count`」兜住该盲区（用例 `tombstone_applied_row_triggers_bucket_recompute`）。已知边界：桶**变空**时不产 chunk，云端空桶对象不主动清理（既有语义，删除由墓碑传播 + pull 差集收敛），列为观察项 N39。
5. **假服务外的真实方言仍是唯一盲区**：F22 修完后 412→CAS 重试路径在假服务上可证，但「某些服务端静默忽略条件头」的行为差异只能靠真服务端（m4 `#[ignore]` 用例保留，跑法见文件头注释）。
