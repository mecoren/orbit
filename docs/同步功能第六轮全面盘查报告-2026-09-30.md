## 一、总体结论

1. **第五轮的 F22-F47 全部核实到位**（含 P0 的包装器转发、分片协议前缀、账本收口、假服务与故障矩阵），本轮**未推翻任何前轮结论**。安全侧（KDF 下限、错误串脱敏、布局版本门禁、AAD 读侧兼容）与 SQLCipher PRAGMA 顺序均正确。
2. **本轮最重缺陷由第五轮的 F41（增量 push 水位线）引入**（F48）：`push` 在「本轮无变化」与「清单已写」两条收尾路径上**无条件推进 `last_pushed_clock_ms`**，未判 `failed_modules`。一旦某表因限流/瞬断上传失败（模块间错误隔离把它降级为 `errors` 而非 `Err`），该表**行数未变**的脏桶会被水位线永久判为「干净」，此后每轮都被 `bucket_is_unchanged` 跳过——**本地编辑静默漏传云端，且不可自愈**。F24 对 `last_synced_at` 建立的「只在不干净轮次之外推进」纪律，**没有同样套用到 F41 新引入的水位线上**。
3. **rekey 的「硬失败防混合态」防线落空**（F49）：`push_all_impl` 仅在**全部**表失败时才不写清单，而 `rekey` 的 `failed_modules > 0` 检查位于 `push_all_force_full` 返回**之后**——此时新 Key 清单已经落盘，云端实际已处于「新 Key 清单 + 旧 Key 分桶」混合态；壳层随后把本机密码回滚成旧密码并回报「已回滚本机密码」，进一步造成本机与云端清单也不同源。
4. **两处「生产链路写出来的令牌与协议要求不符」**（F50/F51）：WebDAV 侧 GET 的 ETag 未走 `normalize_etag`（弱校验前缀 `W/` 被当作令牌字面量发出、空 ETag 得到 `Some("")`）→ 清单 CAS 恒 412 → **清单永不落盘**；S3 侧 canonical URI 直接用 `url::Url::path()`，未按 AWS UriEncode 编码 → `base_path`/对象键含 RFC3986 子分隔符时全量 403。
5. **三处语义/口径不一致**（F52/F53/F54）：设备检查点实际语义是「最后一次 push 时刻」，却被 `tombstone_watermark` 当作「已 pull 到的位置」使用（`push_only` 不 pull 却推进它）；空数据覆盖守卫用「存活行数为 0」判「本地为空」，把「用户合法清空全部数据」误判为删库重装并**永久阻断删除上云**；全量备份导入（整体替换本地数据）不失效同步账本，与 `sync_disconnect` 的处置口径自相矛盾。
6. **观测面缺陷**（F55）：部分失败轮次只发 `Done` 进度帧（`emit_error_on_failure` 只处理 `Err`），UI 显示「同步完成」而同步历史同一条记录是 `failed`——两条口径互相打脸，且后台调度路径不把返回值交给 UI，用户唯一可见信号就是进度帧。
7. **测试面系统性盲区**：F48/F50/F51 的共同成因是**夹具只用安全字符 + 强 ETag + 全成功轮次**——`http_client.rs` 无任何令牌归一化用例、`s3/url.rs` 的 key 全无特殊字符、`push` 无「部分表失败 + 行数不变编辑」用例。三条新 P1 在 CI 上全部体检不出来。
8. 其余 P2/P3 共 27 项，分布在 WebDAV 目录自愈、分片续传自洽性、超时覆盖、备份解码健壮性、内存卫生、跨端契约漂移等面，逐条见 §三。

## 四、重点问题详述

### F48（P1）push 水位线在失败轮次推进 → 编辑永久漏传

**证据链（已逐行核实）**

1. `push.rs:166` 取 `clock_mark = clock::next_ms()`；`push.rs:178` 以 `state.last_pushed_clock_ms` 为水位线扫描脏桶。
2. 表级失败被**降级为 errors 而非 Err**：`push.rs:242-252`（`attempt.failed_modules += 1; attempt.errors.push(...)`）。
3. 「本轮无变化」收尾：`push.rs:269-283`
   ```rust
   let changed_any = force || attempt.pushed_chunks > 0 || attempt.pushed_tombstones > 0;
   if !changed_any {
       ...
       next_state.last_pushed_clock_ms = next_state.last_pushed_clock_ms.max(clock_mark); // ← 无失败判据
       state_store.save(&next_state)?;
       return Ok(result);
   }
   ```
   `changed_any` **不看 `failed_modules`**。
4. 「清单已写」收尾同病：`push.rs:359-365` 同样 `max(clock_mark)`。
5. 下轮的判据盲区：`db_loader.rs:116-119`
   ```rust
   pub fn bucket_is_unchanged(&self, bucket: u32, remote_count: u64) -> bool {
       !self.dirty.contains(&bucket)
           && self.live_counts.get(&bucket).copied().unwrap_or(0) == remote_count
   }
   ```
   行**内容**被改动、行数不变时，`updated_at` 已 ≤ 新水位线 → 不脏；`count` 相等 → 判「逐字节一致」→ 直接 `continue`，**连指纹都不算**（`push.rs:421-428`）。
6. 引擎层不会兜住：`with_retry`（`engine.rs:1428-1431`）见 `Ok` 立即返回，**不重试**「部分失败但整体 Ok」的轮次。

**触发条件（现实可达）**：任意「修改已有行、行数不变」的编辑 → 5 秒防抖的 `sync_on_change` 调 `push_only`（`sync_scheduler.rs:50-113`、`push_only_inner` `engine.rs:601-672`）→ 该桶上传遇 429/瞬断（坚果云 ~1 req/s 限流下 `put_with_retry` 对限流**不做 HTTP 级重试**，直接抛错）→ 该表 `failed_modules=1`，其余 10 表无变化 → 走 `changed_any == false` 收尾 → 水位线推进。

**后果**：该编辑**永不进入云端**；对端 pull 不到；本地下轮报「无变化 → 跳过」，同步历史若无其它错误甚至记为 `success`。恢复只能靠用户再次编辑该行（推进 `updated_at`）或该桶行数发生变化。属**静默、单向、不可自愈的数据丢失**。

**修复方向（建议）**：把 F24 的纪律复制到水位线——推进 `last_pushed_clock_ms` 的前置条件加上 `attempt.failed_modules == 0`；或干脆在 `failed_modules > 0 && changed_any == false` 时走 `Err`（让 `with_retry` 能重试）。**回归**：新增「部分表上传失败 + 行数不变的编辑 → 下轮必须重传该桶」用例（现有 `push.rs` 测试只覆盖全成功轮次）。

### F49（P1）rekey 部分表失败留密钥混合态，且防线位置错误

**证据链**

1. `push.rs:256-265`：只有 `failed_modules == tables.len()`（**全部**失败）才不写清单。
2. `push.rs:285-345`：部分失败照常 `epoch + 1` 并 CAS 上传**用新 Data Key 加密**的清单。
3. `engine.rs:932-957`：`push_all_force_full` 返回**之后**才检查 `push_result.failed_modules > 0` 并 `Err` 中断——此时清单已落盘，防线落空（注释声称「必须硬失败以防混合态」，实现晚了一步）。
4. 分桶路径由桶号决定（`paths::table_bucket_path`），**非内容寻址**，失败表的分桶对象仍是**旧 Key 密文**且路径不变 → 新清单指向旧 Key 密文。
5. 读侧表现：`crypto_io.rs:282-290`（AES-GCM tag 失败 → `KeyMismatch`）→ 全体设备（含本机）被引到恢复页。
6. 壳层掩盖：`sync_crypto_cmd.rs:153-177` 失败即 `change_sync_password(new, old)` 回滚本机 meta，并回报「已回滚本机密码」——但云端清单可能已是新 Key，回滚后**本机反而读不了云端**，文案与事实不符（`orbit-flutter/src/api/sync.rs` 同构，需一并核对）。
7. 叠加项（F64）：`push.rs:398,471` 以远端索引为底 → 「远端有、本机无」的桶被原样保留在新清单里，其对象仍是旧 Key 密文；`push.rs:296-301` 写出的 `manifest_prev.orsync` 是上一版**旧 Key 密文**，rekey 不重加密；legacy `crypto/config` 同样残留。

**触发条件**：v2 改密 / v1→v2 迁移 / 恢复页「以本机为准」期间，任一表上传失败（限流或瞬断）且未达全表失败。

**修复方向**：给 `push_all_impl` 增 `require_all_tables_ok: bool`（rekey 传 true，任一表失败即**在写清单之前**返回 Err）；或把新清单先写 `MANIFEST_PREV_PATH`、全部表成功后才 CAS 主清单（两阶段提交）。同时修正壳层文案为「云端可能已部分重加密，请重试或以本机为准」。回归：注入单表失败 → 断言主清单**未被改写**。

### F50（P1）GET 侧并发令牌未归一化 → 清单 CAS 恒失败

**证据**

- 列举侧：`traits.rs:45-56` `normalize_etag` 剥 `W/` 与引号，空值 → `None`（F26 统一口径）。
- GET 侧：`http_client.rs:185-189`
  ```rust
  .get(reqwest::header::ETAG)
  .and_then(|v| v.to_str().ok())
  .map(|s| s.trim_matches('"').to_string())   // ← 不剥 W/；空串得到 Some("")
  ```
- 该令牌是清单 CAS 的来源：`push.rs:561-574` → `adapter.download_with_token` → `s3_adapter.rs:547-553` / `webdav_adapter.rs:1010-1023`（两者都走 `get_with_token`）。
- 发出侧：`http_client.rs:240-242` `If-Match: "{token}"`。

**后果**：服务端对 GET 回 `W/"abc"`（CDN/反代后常见）时发出 `If-Match: "W/abc"`，强比较恒不匹配 → 每轮 412 → `push.rs:313-337` CAS 重试 3 次后放弃 → **清单永远写不上去**，错误文案却是「并发冲突」，排障方向被带偏。空 ETag 场景同理（`If-Match: ""`）。

**修复方向**：`get_with_token` 改调 `traits::normalize_etag`。回归：`W/"abc"` 与空 ETag 各一条断言（现有 `http_client.rs` 测试完全没碰令牌归一化）。

### F51（P2）SigV4 canonical URI 未按 AWS UriEncode 编码

**证据**：`s3_adapter.rs:94-98` 取 `parsed.path()` 作为 `canonical_uri`；`s3/url.rs:40-75` `build_url` 是纯字符串拼接（`buffer.push_str(path)`），只有 query 段走 `urlencoding::encode`（`:78-86`）。`url` crate 的 WHATWG path 编码集只覆盖 C0/空格/`"`/`#`/`<`/`>`/`?`/`` ` ``/`{`/`}`——`+ & = @ : $ , ; ! ' ( ) *` **一个都不编码**，而 AWS 要求除 `A-Za-z0-9-_.~` 与 `/` 外全部 `%XX`。

**触发**：`base_path` 或对象键含上述字符（如 `base_path = "wait+sync"`、`"a&b"`、`"user@home"`）。中文/空格/`~` 不受影响。

**后果**：客户端签的 canonical URI 与服务端重算结果不符 → 403 `SignatureDoesNotMatch`，表现为「配置看起来完全合法但同步全挂」，且 F34 脱敏后错误串信息量更低。

**修复方向**：实现 `uri_encode(path, encode_slash = false)`（hex 大写、非保留集仅 `A-Za-z0-9-_.~`），**同时**用于实际发出的 URL 与 `canonical_uri`（含 path-style 的 bucket 段）。回归：key 含 `+ & = @ :` 的 canonical request 断言（现有 `s3/url.rs` 测试的 key 全是安全字符，故假绿）。

### F52（P2）设备检查点语义与水位线假设不符

**证据**：`touch_device` 全仓**只有** `push.rs:292` 一处生产调用（`meta.rs:183` 定义，其余为测试）。`pull` 路径从不登记检查点。而 `tombstone_watermark`（`meta.rs:171-180`）取各设备 `last_synced_at` 的**最小值**，`gc.rs:43-56` 据此从清单剔除并删除水位线月份之前的墓碑分桶。

**问题**：水位线的正确性依赖不变量「检查点 = 该设备已 pull 到的位置」。实际语义是「最后一次 push 时刻」，而 `push_only`（`engine.rs:601-672`，on-change 5s 防抖即触发）**只读清单、不应用墓碑**却推进本机检查点——不变量被证伪。

**触发**：≥2 台设备已登记；设备 B 在删除发生之后、任何一次成功 pull 之前，至少做过一次 `push_only`；任一设备再 push 一次（`prune_expired_tombstones` 按 `YYYY-MM` 粒度执行，故需墓碑位于**早于水位线月份**）。三件齐备即：墓碑被 GC，尚未拉到它的设备（及其本地存活行经 push 回流）使已删记录复活。

**修复方向**：`DeviceCheckpoint` 拆 `last_pulled_at` / `last_pushed_at`，水位线只取前者；最小改动是让 `push_only` 不参与 `touch_device`（给 `push_all` 加 `touch_checkpoint: bool`）。第四轮 N13 曾以「所有设备检查点约束在先」为由定为 P3，本项即该前提被破坏的情形——属遗漏而非已知边界。

### F53（P2）空数据覆盖守卫误伤「合法清空全部数据」

**证据**：`push.rs:588-610` 判据为「远端有数据（`remote.tables` 任一非空）+ 本机曾同步过（`last_synced_at > 0 || manifest_epoch > 0`）+ `local_all_tables_empty()`」；而 `local_all_tables_empty`（`push.rs:613-628`）逐表 `SELECT COUNT(*) ... WHERE is_deleted = 0`，**完全不看软删行/墓碑**。

**问题**：远端索引条目一旦存在便**永不消失**（push 以远端为底、桶变空不产 chunk，即 N39 的既有语义），故 `remote_has_data` 对任何曾经有数据的账号恒为真。于是当用户在 11 张可同步表里**把数据全部软删干净**（清空任务/项目/清单/标签/模板/筛选器）时，守卫判「本地为空 + 远端有数据 + 曾同步」→ **阻断 push**，删除永远上不了云，其他设备持续显示已删数据；错误文案把用户导向「从云端恢复」（恰好会把删掉的数据拉回来）或「清除同步状态」。

**关键盲区**：守卫有现成的判别依据却未使用——「本地存在软删行（墓碑）」即可确定是**合法删除**而非删库重装。现有用例 `empty_local_with_remote_data_is_blocked`（`push.rs:1026-1067`）用物理 `DELETE FROM todo_projects` 造态，**天然无法覆盖**「全表软删」这一真实用户路径。

**修复方向**：守卫前置一条「本地存在墓碑（任一可同步表 `is_deleted = 1` 计数 > 0）→ 不阻断」；文案区分两种触发场景。

### F54（P2）全量备份导入不失效同步账本

**证据**：`api/full_sync_backup_api.rs:512-619` 导入流程（事务内逐表 `DELETE FROM` + 插入）**完全未触碰** `SyncStateStore`（该文件 grep `SyncStateStore|sync_state|last_synced_at|manifest_epoch` 零命中）；两条壳层（`full_sync_cmd.rs:75-99,153-185`）也只 `emit("db-change")`。对照 `cloud_sync_cmd.rs:262-265`：`sync_disconnect` 显式 `SyncStateStore::clear()` 并注释「下次配置后触发全量重推」——同一性质的操作（整体替换本地数据）处置口径矛盾。

**后果**：恢复后 `sync_state.json` 仍持恢复前的桶指纹快照与 F41 水位线，`sync_configs.last_synced_at`（回收站物理清理守卫线）同样是旧值。① 恢复出的行 `updated_at` 早于旧水位线、且桶内行数与远端 `ChunkRef.count` 相同时 → 该桶被判「干净」而**漏推**，云端与本地静默分歧；② 守卫线陈旧会让恢复出的软删行被提前物理清理（`trash_api.rs:362-397` 按 `last_synced_at` 放行 `DELETE`），后续 pull 又把它复活。

**修复方向**：导入成功路径末尾统一 `SyncStateStore::clear()` + 重置激活配置 `last_synced_at`（与 `sync_disconnect` 同口径），双端壳保持一致。

### F55（P2）部分失败轮次仍报「同步完成」

**证据**：`engine.rs:422-434` `emit_error_on_failure` 只处理 `Err(_)`；三处 `SyncProgress::Done`（`:560-567`、`:662-669`、`:808-815`）**无条件**发送，不看 `result.errors`。而同一结果在历史表被记为 `failed`（`engine.rs:76-82`）。消费侧 `apps/desktop/src/lib/sync-status.ts:111-114` 把 `done` 映射为「同步完成」。

**后果**：模块间错误隔离（`push.rs:242-252`）产生的部分失败轮次，UI 说「完成」、历史说 `failed`；后台调度路径（`sync_scheduler.rs:182-198`、移动 `sync_on_change_scheduler.dart:97-105`）不把返回值交给 UI，用户唯一可见信号就是进度帧——即被误导为成功。`syncResultSummary` 的「N 个非致命错误」只在手动路径展示。

**修复方向**：`Ok` 且 `!errors.is_empty()` 时也发 `Error` 帧（或新增带摘要的 `DoneWithErrors`），指示器映射为告警态。
