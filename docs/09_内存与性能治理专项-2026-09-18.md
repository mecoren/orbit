## 一、为什么本轮第一件事是建门禁而不是改代码

上一轮（[性能与UX系统性优化报告-2026-09-12.md](性能与UX系统性优化报告-2026-09-12.md) §5.2）
留下的内存数字是「10k 档 169MB used / 257MB total、操作峰 758MB」。本轮开工前先复核该口径，
结论是**这些数字量错了对象**：采样点没有强制 GC，`performance.memory.usedJSHeapSize` 在无 GC
时反映的是「上次回收以来的分配量」——一次万行列表重拉就能把它推高，而实际没有任何泄漏。

同前端同档位、每档采前调 `window.gc()` 后的真实驻留是 **76MB used / 128MB total**（A14 前）。
一个不可复现、且把垃圾读成驻留的基线，会让后续每条「省了多少 MB」的判断都失去意义，
故先落三件工具，之后**任何内存结论必须能被它们复算**；09-12 报告已就地加更正注。

## 二、门禁三件套

| 件 | 位置 | 判据 | CI |
|---|---|---|---|
| 增长曲线 | `perf-metrics/growth-curve.mjs` | 1k/5k/10k 三档 × 3 次取中位，11 项阈值（拦回归）+ 3 项 target（记期望），超阈 exit 1 | `perf-gate` job（ubuntu） |
| 无界审计 | `perf-metrics/audit-unbounded.mjs` | 三条拦停规则 + 一条提示级规则，命中点须带 `bounded*` 标记或在 `knownUnbounded` 登记 | 同一 job，先于曲线跑 |
| exe 口径 | `perf-metrics/memory3.mjs`（既有） | 真机 Tauri 全树 WorkingSet 空闲/峰值 | **不入 CI**（Windows 真机依赖），列入 `docs/08` §正式发布门禁第 1 条 |

基线快照 `perf-metrics/baselines.json`：`thresholds` / `targets` / `measured` / `measuredBeforeA14`
四块分开存。`--record` 只回写 `measured`，其余手工维护。

`growth-curve.mjs` 的几个口径决定，都是踩过之后补上的，改动时别退回旧行为：

- **每档一个全新浏览器上下文**：同页清数据测不出「驻留回不来」，且 React Query 缓存会串档。
- **峰值不 GC、驻留必 GC**：`peakMB_duringChurn` 是 20 次写期间的分配总量（量「重」），
  `leakMB_after20churn` 是强制 GC 后的末样减首样（量「漏」）。两者配对才分得清回归性质。
- **切视图 churn（`switchChurn`）与「多存一份万行」直测（`extraCopyCostMB`）是必需项**：
  只点勾选按钮的 churn 永远走同一个 queryKey，`placeholderData` 那条路径根本不触发——
  A1 落地后首版指标分毫未动，就是栽在这个测量盲区上，而不是假设被证伪。
- **进程 RSS 按 pid 子树收敛**（win32 走 `Get-CimInstance Win32_Process`，posix 走 `ps -eo pid,ppid,rss`）：
  按进程名全局求和会把本机日常浏览器窗口算进指标，门禁立刻失去可复现性。
- **`rssMB_10k` 在 Linux 判 null**：RSS 与窗口/合成器实现强相关，未采到可信数值前不判
  （脚本支持 `thresholdsByPlatform.<平台>` 覆写，`null` = 该平台跳过该项）。

## 四、归因记录（含被本轮证伪的方案预期）

### 4.1 线性项只有一处：逾期置顶段

`domNodes` 在 1k/5k/10k 三档是 1880 / 5471 / 9980——四个视图都过了 `useVirtualizer`，
斜率却非零，说明某处在整列表裸渲染。定位到 `task-list-view.tsx` 的「逾期」置顶分组：
它走裸 `.map()`，注释写着「逾期集天然有限」。**该假设被实测证伪**：10k 档有 334 条逾期，
每行扇出 ~27 个 DOM 节点，且每个节点带 ~4.3KB JS 堆（fiber + hooks 状态 + 监听器 + 样式对象），
于是：

- 常驻堆 37 → 76MB（+39MB，占该档位驻留的一半）；
- 每次写触发的重拉重渲染，多产生 ~12MB 垃圾（20 次勾选的峰值 87 → 327MB）；
- 进程 RSS 356 → 433MB。

归因方法是把种子数据的 `due_date` 整体推到明天再跑一遍同一门禁——DOM 与堆的线性项同时归零，
其余指标不变。A14（置顶段并入同一条虚拟流）即本轮最大单项收益，且**它不是方案里预定的项**，
是门禁首次运行抓出来的。

附带修掉两处同源缺陷：`focusRow` 原先按 `tasks` 取索引而行来自 `rest`，存在逾期行时键盘焦点
落到错位的那一条；置顶段行进流前，虚拟窗整体下偏 `N×57px`（N = 逾期行数），滚动到中段会出空白。

### 4.2 被证伪：A1 的收益量级

方案 §1.1 写「操作峰 758MB 的主体是 `placeholderData` 双份万行数组」。直测一份万行结果集的
边际堆成本 = **2MB**（每行 0.2KB）。双份窗口最多值 2MB，不是 250MB 峰值的来源——峰值来源是 4.1
的置顶段重渲染。A1（大列表去 `placeholderData` + `gcTime` 10min→10s）因此**降级为廉价保险**
保留：它确实消除了一类按参数分叉的长期驻留，但不宣称内存收益，其闪烁代价记进
[04_UI复刻规格-桌面端.md](04_UI复刻规格-桌面端.md)。

### 4.3 对 A2 瘦行的预期要跟着改

一份完整万行结果集深克隆只值 2MB，其中行 DTO 字符串大量走 V8 内部化（同值共享），
砍掉 11 列在 **JS 堆**上的收益上限约 1MB@10k——方案里「JS 169→110MB 主要靠瘦行」的算式作废。
A2 的真实收益在**真机 IPC 字节与解析 CPU**（本门禁的 mock IPC 是进程内调用，测不到序列化），
故 A2 的验收口径应挂 `memory3.mjs` 与 IPC 字节计量，不要用 JS 堆斜率判它的成败。

**实测（2026-09-19，按 4.3 的口径判）**：批2 之后列表通道还剩 26 个键，其中 9 个在列表路径
**零消费**（`uuid`、`description` 外还有 `start_date`、五个 `repeat_*`、`deleted_at`、`version`；
逐消费点核实：重复规则只在详情/表单读 `todoTaskGet` 与 `todo_task_get_detail`，桌面
`setEditingTask` 只被以 `null` 调用故表单不从列表行预取，`sync-conflict-section.tsx` 与
`activity-format.ts` 里的同名字段只是字段名标签表）。万行 × 18 字标题 × 36 字符 uuid 的夹具
下当前线缆 **5.13MB**（批2 报告的 3.85MB 用的是短标题短 uuid 夹具，绝对值随标题长度浮动），
裁掉那 9 列省 **1.98MB（38.6%）**——其中 `uuid` 单列 450KB，其余 8 列省的基本是键名本身
（`"repeat_end_type":0,` 一行 20 字节，值不要钱、键名要钱）。

**结论：本轮不做完整瘦行 DTO**。1.98MB/万次拉取是真实收益，但它要新建 core DTO 并改
`list_todo_tasks` 返回类型，波及面不是镜像链五处而是**双端组件的类型**（桌面十个视图按
`TodoTask` 收 props，移动端 `_mapTask`/`dto.dart` 对每个键硬转型）——按 AGENTS 的口径漂移
判据，最坏失效模式正是我们刚修的这类「字段静默为 null」。同等工力下 A4（干掉两条万行整表
拉取）与 B6（消掉移动端整份万行重复数组）收益更大、风险更小，故 A2 剩余部分**按数字推迟**，
若未来要做：先只裁 `uuid`（单列 450KB、桥层解码改一处）验证镜像链，再谈其余八列。

**2026-10-14 收口（A2 剩余列）**：前置条件（A4/B6 已落地、`uuid` 首步已验证镜像链）具备后
执行，落地方式与上面「波及双端组件类型」的预判一致——**代价如实发生，风险用类型系统对冲**：

- 裁列口径按全仓复核重算：真正零消费的是 **10 列**（`uuid`、`repeat_after`、六个更细的
  `repeat_*`、`deleted_at`、`version`）；本文上一段列的「9 个零消费」把 `start_date` 误算了
  （桌面右键菜单提醒档 `task-context-menu.tsx`、移动 `logic/time_block.dart` 都在列表行上读它），
  `repeat_mode`（移动列表/日历重复徽标）、`created_at`（桌面 `sortTasks`/Logbook/保存筛选器）
  同理必须保留。`description` 保留键、值仍按通道分叉（keyword 通道回真值），否则桌面搜索
  通道的本地收敛分支会把「描述命中」的行二次过滤掉——即 A2 前置修复的回归。
- 桌面把列表路径的共享纯函数（`filterTasks`/`sortTasks`/`applySavedFilter`/`batch-*`/
  `completeTask`/`taskTimeBlock`/`timeslotDropPatch`）与全部列表视图 props 收到
  `TodoTaskListItem = Omit<TodoTask, 10 列>`：`task-panel.tsx` 原先那句
  `(sourceTasks as TodoTask[])` 是唯一入口，撤掉后读被裁列直接 tsc 报错。
- 移动端没有编译期钩子（App 模型是具体类）——用 `TodoTask.listRow` 集中定义回落默认值、
  `_mapTaskRow` 直映 FRB DTO、mock 摘键三处同口径，并以契约用例
  （`bridge_parity_test.dart`）锁定「列表回落默认值 / 单条全列真值」的分界。

**实测（2026-10-14，口径同 `column-prune.mjs`）**：万行夹具走 mock 真实命令面取
`todo_tasks_list` 返回值做 `JSON.stringify`——瘦行（19 键）**3.41MB**，上一版形状
（A2 首步：`uuid` 空串占位、其余 8 列键名俱在，29 键）**5.22MB**，即**每行省 181 字节、
万行省 1.81MB（34.7%）**；181/10 ≈ 18 字节/键，与本节「值不要钱、键名要钱」的判断一致
（该夹具两形状都不传 1KB 描述，故这是纯键名开销）。本机 `node perf-metrics/column-prune.mjs`
起静态服务时页面加载超时（e2e 用的 dev server 正常），数字改用同一数据形状的等价口径取得。

### 4.4 泄漏侧结论

20 次勾选 + 强制 GC 后回落 6MB，写路径没有跨操作存活不释放的容器。本轮所有「内存增长」问题
都属**驻留与重复渲染**，不是泄漏；后续若 `leakMB_after20churn` 越 8MB，优先查模块级 `Map`/`Set`
与按参数分叉的缓存变体（`audit-unbounded` 的拦停规则正是为这两类准备）。

## 五、「无界」的可审计规则（同步进 AGENTS.md）

任何进程生命周期内可达的累加容器——Rust `static`/`Lazy`/`thread_local` 内的集合、
`Mutex`/`RwLock` 包裹且跨调用存活的集合（含 `Arc` 共享的 struct 字段）、跨 hook 存活的模块级
`Map`/`Set`——必须满足三选一并就地标记：

```rust
static X: HashSet<i64> = ...; // bounded: 上限 5000，超出丢最小 id
let y = new Map();            // bounded-by-lifecycle: 组件卸载时 clear
let z = new Map();            // bounded-by-data: 键取自六档优先级枚举
```

`audit-unbounded.mjs` 检查命中点 ±3 行内是否有标记，缺失即拦停；例外只能进
`baselines.json` 的 `knownUnbounded` 登记表，**登记只许降不许升**（棘轮）。
`sql-fetch-all`（无 `LIMIT` 的 `fetch_all`）当前是提示级：存量 19 个文件尚未逐个复核，
A6 落地后连同复核结论一起翻正为拦停。

现状：拦停违例 0 组，登记 **0 组**——`knownUnbounded` 已清空（棘轮到零）。
2026-10-12 复核收口 2 组：`reminderToastIds` 补 `onDismiss` 手动划掉路径后标
`bounded-by-data`（此前每手动划掉一个常驻 toast 残留一项）、`activity-format.ts`
的 `TARGET_ACTIONS` 字面量枚举 Set 标 `bounded-by-data`。
2026-10-14 A7 收口最后 2 组（两份 `NOTIFIED_REMINDERS`，见 §六 A7 行）。

**A13（附件零拷贝）2026-10-14 落地（按收益重估后只做有效的那一半）**：第五轮 N40 的原方案
是「reqwest `stream` + 把适配器 trait 的 `Vec<u8>` 全换异步读」，本轮逐段核账后发现——
附件是 AES-256-GCM **整包 AEAD**，解密必须持有完整密文，**流式下载到文件对峰值毫无收益**
（真流式解密要手搓 GHASH，宁可不做）；真正在吃内存的是**上传侧的三份载荷**。故落地：

1. **HTTP 请求体改 `Bytes`**（`http_client.rs` 的 `put_with_retry` / `put_conditional`）：
   重试时 `.body(body.clone())` 由整包复制退化为引用计数自增（大附件单 PUT 4 次尝试原本
   最多复制 4 份载荷）。
2. **所有权移交通道**：trait 新增 `upload_owned(path, Vec<u8>)`（默认退回借用版，未覆盖者
   行为与成本不变），`upload_asset` 入参 `&[u8]` → `Vec<u8>`；WebDAV / S3 覆盖
   `upload_owned`，用 `Bytes::from(Vec)` **零拷贝**接管附件加密产物；两适配器的单 PUT
   逻辑各自抽成 `put_object_bytes`，避免借用/移交两份拷贝漂移。
3. **附件路径及时释放缓冲**（`cloud_sync/attachments.rs`）：上传的明文在加密后立刻 drop、
   下载的密文在解密后立刻 drop——原本二者分别横跨整段网络上传与校验落盘。大附件峰值
   驻留由「明文 + 密文 + 请求体副本」降到「密文一份」。

**A13 第二拍（下载侧，2026-10-14）**：`HttpClient::get_with_retry` / `get_with_token` 与
适配器 trait 的 `download` / `download_asset` / `download_with_token` 全部返回 `Bytes`
（reqwest 的 `resp.bytes()` 本就是 `Bytes`，此前 `to_vec()` 为每个下载对象——分桶 / 清单 /
附件——多复制一份整包）。收益与上传侧同量级：分桶与清单是小对象，附件是数十 MB 级。
各处适配：WebDAV 分片拼装改为 `extend_from_slice` + 末尾 `Bytes::from(assembled)`（拼装
本身是分片协议固有的复制）；`push::read_remote_manifest_opt` 的回滚点原始密文同步改
`Option<Bytes>`；`full_sync_backup_api::download_cloud_backup` 保留 `Vec<u8>` 返回（字节要
交给双端壳继续持有，属既有 API 边界，`to_vec()` 是边界转换而非链路内复制）。

ADR 0010 §四对 A10/A13「指纹相等、零上传」归因信号的要求在本批不冲突——两拍都只减内存
复制，不改云端对象格式与上传判定口径。

**A10（同步字节复用）第五轮已落地**（F40 + F41，2026-09-19）：
- F40：一轮同步的 raw/包装适配器共享同一底层实例（`create_adapters`，一 run 一 Client，
  phase 间复用热连接）；附件 push 无待传项时早退跳过 `list_assets`（本就在 `:90` 早退，
  本轮补指针相等回归 `adapters_share_single_underlying_instance`）。
- F41：push 只对「水位线之后有写入、或行数与上次推送不一致」的桶重算指纹与序列化，
  其余桶沿用远端清单条目（零 JSON 化、零 sha256）。
  **复算口径**（10k 行库「改一行后同步」）：改动前每轮序列化 = 全部存活行（~10k 行）
  + 64 桶 canonical 哈希 + 64 桶载荷序列化；改动后 = 1 个桶（~156 行）序列化 +
  1 次 canonical 哈希，其余 63 桶零计算（`skipped_chunks` 计数可见）；
  另每表一次 `SELECT uuid, updated_at WHERE is_deleted = 0` 的轻量列扫描（不物化整行）。
  **水位线 = `SyncState.last_pushed_clock_ms`**（push 成功时推进到 push 开始时的时钟快照），
  与 pull 侧冲突判据 `last_synced_clock_ms` **刻意分离**——后者在 pull 结束推进到本轮结束时刻，
  复用它会把「本轮开始前的本地编辑」判成非脏而漏传。
  判据是「时间戳（updated_at > 水位线）∪ 行数（≠ 远端 ChunkRef.count）」的并集：
  单靠时间戳会漏掉 merge 应用远端墓碑造成的本地软删（行时间戳锚定墓碑的 deleted_at，
  可能早于水位线），行数比对正是补这个盲区（用例 `tombstone_applied_row_triggers_bucket_recompute`）。
  A10 依赖的「指纹相等 → 零上传」归因基线未被污染：指纹口径（排除 updated_at/id）未动，
  桶内容语义未动（`bucket_is_unchanged` 只决定「是否重算」，重算结果仍与远端 fp 逐字比对）。

### 8.2 操作级探针（首轮，2026-10-23）

口径：`crates/orbit-core/examples/operation_probe.rs` 每场景独立进程；
`allocPeakDeltaMB` = 自定义 `GlobalAlloc` 记录的**净分配峰值增量**（主指标，不受

| 备份导出（v2 本地） | 5.7MB | +5.8MB | +3.8MB | 649ms | ≤128MB | ✅ 本规模达标 |

读法与边界：

- **附件写入曾是四场景里唯一还有「真实可打爆内存面」的一条**：`add_task_attachment`
  入参是 `&[u8]`，调用方先 `fs::read` 整文件、core 再落盘；50MB 附件因此稳定多出
  一份整文件峰值。它正是 T1.1（M3）的 before 列；M3 落地后已降到 +0.4MB，`thresholds`
  从 60MB **收紧到 8MB**（见 §8.4）。
- **备份与 CSV 的「达标」只对本规模成立**：当前备份仅 5.7MB、CSV 1.8MB，128MB/64MB
  的验收线真正要验的是「峰值不随体积增长」的**斜率**；200MB 级备份的斜率对比
  归 T1.2（云端流式化）的样本扩展，100k 行 CSV 属 M2 的补充样本——两者都还没到，
  不要把本表读成验收已完成。
- **CSV 的 80s 是逐行事务的耗时**，不是内存问题：`execute_csv_import` 每行独立成败，
  20k 行写入约 80s；探针把时长单列，不用它判内存回归。
- `durationMs` 与 `artifactMB` 不进阈值（机器负载/固定数据规模决定）；thresholds 只
  登记 `allocPeakDeltaMB` / `rssPeakDeltaMB` 八项，脚本内再乘 15% 缓冲带。

| 附件导出（流式 copy） | 50MB | +0.3MB | +0.3MB | 39ms | ≤32MB | ✅ 达标 |

| 附件拉回（流式解密） | 50MB | +8.0MB | +8.3MB | 472ms | ≤32MB | ✅ 达标 |

读法与边界：

- **写入/导出**的峰值只剩 256KiB 复制缓冲，与文件大小完全解耦；桌面壳已改成
  路径入参（文件选择器）与导出预览（非图片/大图片），IPC 不再搬运整份字节。
- **推送 12MB** 主要是一帧明文（4MiB）+ 一帧密文（4MiB+16B）+ 加密/哈希临时缓冲；
  拉回 8MB 是密文帧 + 明文帧 + sha256 增量状态。两者都随**帧大小**而非附件大小增长。
  RSS 是 10ms 采样，随机器负载有 ±2MB 波动（复跑推送 RSS 见 10.3MB，堆峰值稳定 12MB）。
- **并发与预算**：默认 2 路 + 64MiB 在途字节预算（`AttachmentTransferLimits`）。
  50MB 单件按预算上限放行（40→64 单位取 50），两个 50MB 不会同时进入
  「加密+上传」临界区；预算只在 push 侧按明文大小加权，pull 侧因云端列表不含大小
  按 1 单位申请，实际峰值由帧大小约束。
- **旧对象**：存量 `OSZS` 云端附件仍可读（整包路径，峰值=对象大小），下一次重传
  自然转为 `OSAC`；不做主动迁移。
- **门禁**：`perf-metrics/operation-baselines.json` 的 thresholds 已按本表收紧
  （写入/导出 8MB、推送 24MB、拉回 20MB），targets 四条均为 32MB。

### 8.5 大库验收：223MB 备份与 50k 首同步（T0.2 + T1.2，2026-10-23）

补上两条一直缺尺子的验收：`backup-export-large`（50k 行 × 4KiB 描述，
产物 **222.9MB**）与 `initial-sync`（50k 行、云端为空、丢弃型适配器只统计
上传字节）。`initial-sync` 真实走 `push_all` 的「分桶扫描 → 逐桶装载 →
加密 → 上传」，只把网络/磁盘写入换成内存丢弃，以隔离 I/O 噪声。

| 场景 | 产物 | 堆峰值增量 | RSS 峰值增量 | 阶段时长 | 验收线（RSS） | 判定 |
|---|---|---|---|---|---|---|
| 大库备份导出 | 222.9MB | +7.8MB | +14.0MB | 6.6s | ≤128MB（T1.2） | ✅ 达标 |
| 50k 首同步 | 22.5MB 库 / 上传 2.3MB / 65 桶 | +9.1MB | +31.5MB | 22.1s | ≤128MB（#91） | ✅ 达标 |

读法：

- **大库备份**：峰值只剩「500 行分页 + 4MiB 帧 + 写盘缓冲」，223MB 产物与
  5.7MB 小样本的堆峰值（+5.8MB）几乎同量级——M1 的「斜率≈0」在 40 倍
  体积上成立。RSS 反而比首同步低，因为导出不查库、顺序写盘，页缓存压力小。
- **50k 首同步**：堆峰值 9.1MB ≈ 单桶（约 781 行 JSON）+ 一个加密帧；65 桶
  依次装载/释放，没有整表驻留。RSS 的 31.5MB 大头是 SQLite page cache 与
  分配器驻留，不随行数线性增长（可对照 M4 前后：整表 `Vec<Value>` 方案在
  50k 行会多出数十 MB 常驻）。
- **边界**：丢弃型适配器不测真实 WebDAV/S3 的 50k 首同步；网络与重试会拉长
  时长，但内存峰值由「装载 + 加密」决定，与协议无关。云端 200MB 级备份的
  上传流式已由 `#89` 的三协议覆盖，本表只验本地导出侧。
- **门禁**：`operation-baselines.json` 新增 4 项阈值（大备份 20/30MB、首同步
  24/60MB），targets 两条均 128MB；`--only` 定向跑与 `--record` 合并写回
  保证单场景调试不会清掉其他基线。
