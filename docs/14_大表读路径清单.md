# 大表读路径清单（M4 审计分类）

> 来源：`docs/13 §6.2 M4` 第 2 点「对 `sql-fetch-all` 提示逐项分类」。
> 口径：`perf-metrics/audit-unbounded.mjs --gate` 报出的 `sql-fetch-all` 组
> （当前 18 组 / 57 处）。**本清单不是白名单**——`sql-fetch-all` 是提示级
> （`blocking:false`），拦停只对「常驻无界结构」生效。
>
> 维护规则：**新增 `fetch_all` 必须在本表登记一行并说明数据上界**。
> 没有上界的一律改分页/流式，不能靠「暂时没出事」蒙混。

## 一、分类口径

| 档 | 含义 | 处置 |
|---|---|---|
| **A 合法全表** | 该读路径的**目的**就是拿全表（备份导出、明文导出、同步装载、表结构元数据） | 保留；已在 M1/M4 中把「整包/整表驻留」改为分页或逐桶 |
| **B 可加 LIMIT** | 读路径面向 UI 列表，天然有上限但 SQL 没写 | 保留现状 + 登记；后续按需收紧 |
| **C 天然有界** | 表本身行数极小（配置项、迁移元数据）或查询带固定枚举条件 | 保留，标注「数据源天然有界」 |
| **D 只读聚合** | 统计类，理论上可流式累加 | 现状物化；行数由业务规模决定，暂不阻断 |

## 三、M4 落地后的变化

- `db_loader.rs` 的 7 处 `fetch_all` **仍在**，但语义已变：其中 1 处是 uuid 索引
  （只读一列，几百 KB 级），其余是按 uuid 批量取行（每批 500）。
  **整表 `Vec<Value>` 常驻已消除**——这是 M4 的实质收益。
- 审计提示数量未下降（仍 18 组）：`sql-fetch-all` 是**静态规则**，看不见
  「逐桶调用」这层运行时语义。故本清单是必要的补充说明，而不是靠改代码
  去讨好规则。
- **50k 首同步实测（2026-10-23，T0.2）**：`operation-probe.mjs --only initial-sync`
  在 50k 行 / 22.5MB 库上跑完整 `push_all`（云端为空、上传丢弃），堆峰值
  **+9.1MB**、RSS 峰值 **+31.5MB**、65 桶、上传 2.3MB，22.1s。验收线 128MB，
  余量约 4 倍。RSS 的大头是 SQLite page cache 与分配器驻留，不是装载链路——
  与「逐桶只驻留一个桶」的预期一致。

## 四、后续新增 `fetch_all` 的自检问题

写新的 `fetch_all` 前先回答三个问题：

1. **数据上界是什么？**（表行数上限 / 查询条件上限 / 固定枚举）
2. **这个上界是编译期已知，还是随用户数据增长？** 后者必须改分页或流式。
3. **如果它失败（表损坏/超大），失败模式是什么？** 静默返回空集是最坏的
   一种——那会把「读不到」伪装成「没有数据」。
