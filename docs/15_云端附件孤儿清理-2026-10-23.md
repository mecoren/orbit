## 一、背景与问题

附件云端通道当前**只增不删**:

- `SyncAdapter` 只有通用 `delete(path)`(`crates/orbit-core/src/sync_adapters/traits.rs:171-172`),其生产调用方是 `cloud_sync/gc.rs`(数据分桶)与 `push.rs`(清单对账),**均不涉及 `assets/`**;
- 附件同步仅有 push/pull 两个入口(`crates/orbit-core/src/cloud_sync/attachments.rs:138/374`),无删除分支;
- `gc_local_attachments` / `delete_unused_attachments` 明示云端保留(`crates/orbit-core/src/api/asset_api.rs:534-567/604-650`);
- 这是 docs/07 #33 落地时的**刻意决策**:多设备引用计数不可靠,「宁可多留孤儿,不做误删」。

随着两件事落地,本地侧已可收敛而云端不可收敛:

1. 回收站彻底删除物理清理附件链行(trash_api 三处 purge,2026-10-23);
2. 诊断页「清除未使用附件」手动清理无引用附件(2026-10-23)。

**代价**(只影响用户自己的网盘/S3 桶,不影响功能正确性):

- 配额只增不减——含已删任务、换附件、上传中断残留、以及本地清掉的「未使用附件」的云端副本;
- 每轮同步 `list_assets` 全量列举 `assets/` + `assets_parts/`(WebDAV 两次 PROPFIND、S3 按 1000/页翻页),对象数线性拖慢同步前置;
- pull 差集有 `active_refs` 过滤(`attachments.rs:435-462`),孤儿不会被拉回——所以不会引发磁盘/流量循环,纯占空间。

#33 的「引用计数不可靠」前提可以解除:**`todo_task_attachments` 本身是 SYNCABLE_TABLES 第 9 表、随 todos 模块同步**(`crates/orbit-core/src/cloud_sync/modules.rs:51-52`),云端 `tables/todo_task_attachments/` 分桶就是**跨设备并集的权威引用集**——本机视角的「无引用」不可信,云端视角的「无引用」可信。

## 二、目标与非目标

**目标**

1. **只读扫描**:列出云端孤儿附件(裸 hash、密文体积、mtime、整包/分片形态、本地账本状态),按体积降序;
2. **手动删除**:勾选批量删除 + 「全部删除」,覆盖整包与分片两形态,危险确认 + 秒级冷静期;
3. **自愈对账(必备配套,不是可选)**:pull 侧「活跃引用 + 云端缺失 + 本地有文件」→ 置 `is_uploaded = 0` 触发下轮重传——封住「清理后他设备引用复活」的竞态真丢;
4. **本地账本收尾**:云端删除成功后,本地 `sys_attachments` 对应行按原子复核清理,防幽灵行。

**非目标**

- 不做自动/定时云端 GC——本地优先,删除时机归用户(与「不做自动更新轮询」同口径);
- 不做桶内容墓碑二次判据(#96 未做,同样不做:清单已是唯一真相源);
- 不做云端容量全景/对象浏览器——只做孤儿清单;
- 不碰 `tables/`、`tombstones/` 目录——那是 #96(`collect_and_delete_orphan_chunks`,已就绪未接线)的地盘,只共享入口卡片。

## 四、多设备安全分析

### 4.1 判据

```
云端孤儿 = (assets/ 对象 ∪ assets_parts/ 分片目录) − 云端引用集
云端引用集 = tables/todo_task_attachments 数据桶(清单索引的 64 桶)中 is_deleted=0 行的 DISTINCT hash
```

要点:

- **以云端表为准,不用本机表**:本机「无引用」只是本机视角(离线设备的行可能还没同步上来);云端桶是各设备 push 合并后的并集,行还在 = 有设备引用,不清;
- **墓碑行不算引用**:数据桶行 `is_deleted=1`(或墓桶条目)即已删除,允许清——与本地 `gc_local_attachments`/`delete_unused_attachments` 的口径逐字一致;
- **清单索引桶之外的桶不参与引用集**(孤儿桶,#96 会收):无清单引用即不可达,任何设备都读不到其中行,以其内容作判据等于把不可达数据当真相。

### 4.2 离线设备与传播窗口(为什么窗口是 30 天)

删除一附件链行的传播链:发起设备 push(数据桶剔除该行、墓桶加条目)→ 云端引用集立刻失去该 hash → 附件可被判孤儿。但另一台**离线设备**可能:

- 本地链行仍 `is_deleted=0`、且本地附件文件已被 LRU 逐出(`is_local_cached=0`,依赖云端回拉)→ 云端对象被删后它**真丢**;
- 本地仍有明文文件 → pull 时「活跃引用 + 云端缺失」被自愈逻辑置 `is_uploaded=0`,下轮 push 重传,云端对象回来,**自愈闭环**。

数据桶孤儿(#96)有清单兜底——「无引用即不可达」,删了不影响任何读路径;附件对象删了就是没了。所以默认窗口从 #96 的 24h 放宽到 **30 天**(`const CLOUD_ASSET_MIN_AGE_SECS`,测试注入),覆盖:墓碑传播窗口 + 用户后悔窗口 + 长假离线窗口。残余真丢窗口(离线超 30 天 + 本地无明文)写进确认弹窗文案,由用户裁决。

### 4.3 三重误删兜底

1. **mtime 窗口**:对象 `last_modified <= 0`(服务端不回时间)一律跳过,新于窗口的对象留给下一轮(照抄 `gc.rs:180-184` 口径);
2. **epoch 复核**:删除执行前重拉清单,`epoch` 与扫描时不一致(期间有设备 push 过)→ 拒绝执行并要求重扫——push 改任何桶内容必改清单指纹,epoch 变化即引用集可能已变;
3. **仅手动触发**:无任何自动路径;UI 走 `DangerousConfirmDialog` 秒级冷静期,文案明示「云端密文对象将被删除;已无本地副本的附件将永久无法恢复」。

### 4.4 删除顺序与失败语义

- 分片形态:**先删 `head.json`**(清单消失即目录立即不可读,对齐 `webdav_adapter.rs:1034`)→ 再逐 `*.bin`;中断残留的分片不可读、不参与 `list_assets` 并集之外的任何路径,无害;
- 整包形态:直接删 `assets/{hash}.orsync`;
- 404 当成功(`delete` 已幂等);单对象失败只记 `errors` 不中断(对齐 `delete_orphan_chunks`);
- **不先删本地、不先改清单**:附件不在同步清单里,不存在「清单引用但对象已删」的中间态,顺序约束比 #96 简单。

### 4.5 自愈(与删除同批,封竞态)

竞态:扫描 → 用户确认(人停留,分钟级)→ 删除之间,另一设备 push 了引用旧 hash 的新任务(同内容重传,hash 相同)。epoch 复核把窗口收窄到秒级,但 pull 阶段仍可能撞上「引用刚到、对象已删」。故 `sync_attachments_pull_with_limits` 尾部新增对账:

```
heal = active_refs − cloud_hashes
heal 中 is_local_cached=1 的行 → 置 is_uploaded=0(下轮 push 自动重传,内容寻址保证 hash 不变)
heal 中 is_local_cached=0 的行 → 记入 result.errors(「附件云端缺失且本地无副本」,UI 可见,不可自愈)
```

`mark_uploaded`/`upsert` 已有,只差一个 `mark_pending_reupload`(UPDATE ... SET is_uploaded=0 WHERE hash=? AND is_local_cached=1)。该自愈同时覆盖历史场景:用户手工在网盘端删过 `assets/` 对象(现状是静默缺附件、永不补传,见 §三缺口 ②)。

### 4.6 本地账本收尾

云端删除成功后,本地 `sys_attachments` 对应行若仍存在,按 `delete_unused_attachments` 同款 `DELETE ... WHERE NOT EXISTS(存活链行)` 原子复核清理(`asset_api.rs:625-636`)——防「清理期间附件被重新挂载」的误删,同时消掉「云端无对象、本地幽灵行」的状态(`is_uploaded=1` 指向不存在对象,LRU 逐出与诊断读数都会失真)。

## 五、方案设计

### 5.1 core 原语(`orbit-core`,全部业务下沉)

新文件 `crates/orbit-core/src/cloud_sync/asset_gc.rs`(与 `gc.rs` 并列,文件头 `//!` 写明判据/窗口/顺序约束):

```rust
/// 云端孤儿附件视图(扫描结果行,可序列化过桥)
pub struct CloudAssetOrphanView {
    pub hash: String,
    /// 密文体积(整包=对象长度;分片=head.json#size)
    pub cipher_bytes: u64,
    /// 服务端 mtime(Unix 秒;<=0 表示不可得——扫描行仍展示,删除判据另行跳过)
    pub last_modified: i64,
    /// 整包 / 分片
    pub kind: CloudAssetKind,
    /// 本地账本状态(来自 sys_attachments,缺行=账本无记录)
    pub is_local_cached: bool,
    pub is_uploaded: bool,
}

/// 只读扫描:云端对象集 − 云端引用集 −(可选)本地复核
pub async fn scan_cloud_orphan_assets(...) -> CoreResult<Vec<CloudAssetOrphanView>>;

/// 删除:epoch 复核 + 逐 hash 两形态删除 + 本地账本收尾
pub async fn delete_cloud_orphan_assets(...) -> CoreResult<CloudAssetDeleteResult>;
```

扫描内部顺序:

1. 拉云端清单(记下 epoch);
2. 遍历清单 `tables["todo_task_attachments"]` 索引桶:下载 → `decrypt_bucket_payload` → 解析行 → 收集 `is_deleted=0` 的 hash(**逐桶即抛**,峰值 O(单桶行));
3. `list_assets_with_meta` 列对象集(见 5.2);
4. 差集 + mtime 窗口过滤 + 按 `cipher_bytes` 降序。

删除内部顺序:重拉清单比对 epoch → 逐 hash:分片先 `head.json` 后 `*.bin`,整包直接删 → 全部成功后对存活链行复核清账本行 → 汇总 `deleted / skipped(重扫) / errors`。

### 5.2 适配器层:新增带元数据的资产列举

`SyncAdapter` 新增方法(与 `list_assets` 并列,同样由 `BasePathAdapter` 显式转发,`cloud_sync_api.rs:163-169` 同款):

```rust
/// 列出云端附件对象及元数据(hash/密文长度/mtime/形态)
/// 返回值与 list_assets 同域(裸 hash),WebDAV 须并集 assets_parts/(S4 口径)
async fn list_assets_with_meta(&self, assets_dir: &str)
    -> Result<Vec<RemoteAssetObject>, SyncError>;
```

- WebDAV:`assets/` PROPFIND Depth:1(条目含 getcontentlength/getlastmodified)+ `assets_parts/` 两层(hash 目录名 + head.json 条目的 mtime/size);
- S3:prefix 分页列举(`ListObjectsV2` 自带 Size/LastModified),整包直取、分片按 `{hash}/` 前缀聚合(体积求和、mtime 取最大);
- **分片体积在 WebDAV 侧不可得**(目录条目不回 getcontentlength):`cipher_bytes` 记 0,UI 用本地账本 `size_bytes` 兜底展示——不为体积额外发 N 次 GET;
- 默认实现退化为「`list_assets` + 全零元数据」(mock 友好,生产必覆盖);
- `RemoteAssetObject { hash, cipher_bytes, last_modified, kind }` 定义在 `sync_adapters/traits.rs`。

- 扫描判据:云端引用集含 hash 不判孤儿;墓碑行(`is_deleted=1`)不构成引用;清单索引外桶的行不参与引用集;mtime 缺失/新于窗口的跳过;体积降序;

- 自愈:本地有文件 → 置 `is_uploaded=0` 且下轮 push 真重传;本地无文件 → 记 error 不动账本;
- 账本收尾:被重新挂载的 hash 账本行不删(NOT EXISTS 复核)。

**`sync_fault_matrix`(FakeCloud,网络级)**:WebDAV/S3 各三例——孤儿(旧)被删且云端对象数下降;清单引用保留;孤儿(新,窗口内)保留。夹具沿用 #96 修正后的形态(对象键 percent-decode + 前导斜杠)。

**桌面**:ipc-mock 口径漂移用例(扫描判据与 core 同款);清单分组/体积汇总/选择态纯函数共置 `.test.ts`。

## 八、风险与回滚

| 风险 | 等级 | 缓解 |
|---|---|---|
| 误删仍被引用的附件 | 高(数据丢失) | 云端权威引用集 + epoch 复核 + 30 天窗口 + mtime 缺失跳过 + 仅手动 + 冷静期;竞态兜底靠自愈(§4.5) |
| 离线超窗口 + 本地无明文 → 真丢 | 中 | 确认弹窗明示;30 天默认窗;用户裁决 |
| S3 head.json 下载读体积的额外 GET | 低 | 仅分片形态、单次小对象;失败时体积记 0 不阻塞 |
