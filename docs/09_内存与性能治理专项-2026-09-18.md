## 一、为什么本轮第一件事是建门禁而不是改代码

上一轮（[性能与UX系统性优化报告-2026-09-12.md](性能与UX系统性优化报告-2026-09-12.md) §5.2）
留下的内存数字是「10k 档 169MB used / 257MB total、操作峰 758MB」。本轮开工前先复核该口径，
结论是**这些数字量错了对象**：采样点没有强制 GC，`performance.memory.usedJSHeapSize` 在无 GC
时反映的是「上次回收以来的分配量」——一次万行列表重拉就能把它推高，而实际没有任何泄漏。

同前端同档位、每档采前调 `window.gc()` 后的真实驻留是 **76MB used / 128MB total**（A14 前）。
一个不可复现、且把垃圾读成驻留的基线，会让后续每条「省了多少 MB」的判断都失去意义，
故先落三件工具，之后**任何内存结论必须能被它们复算**；09-12 报告已就地加更正注。

## 二、门禁三件套

| 件 | 位置 | 判据 | CI |
|---|---|---|---|
| 增长曲线 | `perf-metrics/growth-curve.mjs` | 1k/5k/10k 三档 × 3 次取中位，11 项阈值（拦回归）+ 3 项 target（记期望），超阈 exit 1 | `perf-gate` job（ubuntu） |
| 无界审计 | `perf-metrics/audit-unbounded.mjs` | 三条拦停规则 + 一条提示级规则，命中点须带 `bounded*` 标记或在 `knownUnbounded` 登记 | 同一 job，先于曲线跑 |
| exe 口径 | `perf-metrics/memory3.mjs`（既有） | 真机 Tauri 全树 WorkingSet 空闲/峰值 | **不入 CI**（Windows 真机依赖），列入 `docs/08` §正式发布门禁第 1 条 |

基线快照 `perf-metrics/baselines.json`：`thresholds` / `targets` / `measured` / `measuredBeforeA14`
四块分开存。`--record` 只回写 `measured`，其余手工维护。

`growth-curve.mjs` 的几个口径决定，都是踩过之后补上的，改动时别退回旧行为：

- **每档一个全新浏览器上下文**：同页清数据测不出「驻留回不来」，且 React Query 缓存会串档。
- **峰值不 GC、驻留必 GC**：`peakMB_duringChurn` 是 20 次写期间的分配总量（量「重」），
  `leakMB_after20churn` 是强制 GC 后的末样减首样（量「漏」）。两者配对才分得清回归性质。
- **切视图 churn（`switchChurn`）与「多存一份万行」直测（`extraCopyCostMB`）是必需项**：
  只点勾选按钮的 churn 永远走同一个 queryKey，`placeholderData` 那条路径根本不触发——
  A1 落地后首版指标分毫未动，就是栽在这个测量盲区上，而不是假设被证伪。
- **进程 RSS 按 pid 子树收敛**（win32 走 `Get-CimInstance Win32_Process`，posix 走 `ps -eo pid,ppid,rss`）：
  按进程名全局求和会把本机日常浏览器窗口算进指标，门禁立刻失去可复现性。
- **`rssMB_10k` 在 Linux 判 null**：RSS 与窗口/合成器实现强相关，未采到可信数值前不判
  （脚本支持 `thresholdsByPlatform.<平台>` 覆写，`null` = 该平台跳过该项）。

## 四、归因记录（含被本轮证伪的方案预期）

### 4.1 线性项只有一处：逾期置顶段

`domNodes` 在 1k/5k/10k 三档是 1880 / 5471 / 9980——四个视图都过了 `useVirtualizer`，
斜率却非零，说明某处在整列表裸渲染。定位到 `task-list-view.tsx` 的「逾期」置顶分组：
它走裸 `.map()`，注释写着「逾期集天然有限」。**该假设被实测证伪**：10k 档有 334 条逾期，
每行扇出 ~27 个 DOM 节点，且每个节点带 ~4.3KB JS 堆（fiber + hooks 状态 + 监听器 + 样式对象），
于是：

- 常驻堆 37 → 76MB（+39MB，占该档位驻留的一半）；
- 每次写触发的重拉重渲染，多产生 ~12MB 垃圾（20 次勾选的峰值 87 → 327MB）；
- 进程 RSS 356 → 433MB。

归因方法是把种子数据的 `due_date` 整体推到明天再跑一遍同一门禁——DOM 与堆的线性项同时归零，
其余指标不变。A14（置顶段并入同一条虚拟流）即本轮最大单项收益，且**它不是方案里预定的项**，
是门禁首次运行抓出来的。

附带修掉两处同源缺陷：`focusRow` 原先按 `tasks` 取索引而行来自 `rest`，存在逾期行时键盘焦点
落到错位的那一条；置顶段行进流前，虚拟窗整体下偏 `N×57px`（N = 逾期行数），滚动到中段会出空白。

### 4.2 被证伪：A1 的收益量级

方案 §1.1 写「操作峰 758MB 的主体是 `placeholderData` 双份万行数组」。直测一份万行结果集的
边际堆成本 = **2MB**（每行 0.2KB）。双份窗口最多值 2MB，不是 250MB 峰值的来源——峰值来源是 4.1
的置顶段重渲染。A1（大列表去 `placeholderData` + `gcTime` 10min→10s）因此**降级为廉价保险**
保留：它确实消除了一类按参数分叉的长期驻留，但不宣称内存收益，其闪烁代价记进
[04_UI复刻规格-桌面端.md](04_UI复刻规格-桌面端.md)。

### 4.3 对 A2 瘦行的预期要跟着改

一份完整万行结果集深克隆只值 2MB，其中行 DTO 字符串大量走 V8 内部化（同值共享），
砍掉 11 列在 **JS 堆**上的收益上限约 1MB@10k——方案里「JS 169→110MB 主要靠瘦行」的算式作废。
A2 的真实收益在**真机 IPC 字节与解析 CPU**（本门禁的 mock IPC 是进程内调用，测不到序列化），
故 A2 的验收口径应挂 `memory3.mjs` 与 IPC 字节计量，不要用 JS 堆斜率判它的成败。

**实测（2026-09-19，按 4.3 的口径判）**：批2 之后列表通道还剩 26 个键，其中 9 个在列表路径
**零消费**（`uuid`、`description` 外还有 `start_date`、五个 `repeat_*`、`deleted_at`、`version`；
逐消费点核实：重复规则只在详情/表单读 `todoTaskGet` 与 `todo_task_get_detail`，桌面
`setEditingTask` 只被以 `null` 调用故表单不从列表行预取，`sync-conflict-section.tsx` 与
`activity-format.ts` 里的同名字段只是字段名标签表）。万行 × 18 字标题 × 36 字符 uuid 的夹具
下当前线缆 **5.13MB**（批2 报告的 3.85MB 用的是短标题短 uuid 夹具，绝对值随标题长度浮动），
裁掉那 9 列省 **1.98MB（38.6%）**——其中 `uuid` 单列 450KB，其余 8 列省的基本是键名本身
（`"repeat_end_type":0,` 一行 20 字节，值不要钱、键名要钱）。

**结论：本轮不做完整瘦行 DTO**。1.98MB/万次拉取是真实收益，但它要新建 core DTO 并改
`list_todo_tasks` 返回类型，波及面不是镜像链五处而是**双端组件的类型**（桌面十个视图按
`TodoTask` 收 props，移动端 `_mapTask`/`dto.dart` 对每个键硬转型）——按 AGENTS 的口径漂移
判据，最坏失效模式正是我们刚修的这类「字段静默为 null」。同等工力下 A4（干掉两条万行整表
拉取）与 B6（消掉移动端整份万行重复数组）收益更大、风险更小，故 A2 剩余部分**按数字推迟**，
若未来要做：先只裁 `uuid`（单列 450KB、桥层解码改一处）验证镜像链，再谈其余八列。

### 4.4 泄漏侧结论

20 次勾选 + 强制 GC 后回落 6MB，写路径没有跨操作存活不释放的容器。本轮所有「内存增长」问题
都属**驻留与重复渲染**，不是泄漏；后续若 `leakMB_after20churn` 越 8MB，优先查模块级 `Map`/`Set`
与按参数分叉的缓存变体（`audit-unbounded` 的拦停规则正是为这两类准备）。

## 五、「无界」的可审计规则（同步进 AGENTS.md）

任何进程生命周期内可达的累加容器——Rust `static`/`Lazy`/`thread_local` 内的集合、
`Mutex`/`RwLock` 包裹且跨调用存活的集合（含 `Arc` 共享的 struct 字段）、跨 hook 存活的模块级
`Map`/`Set`——必须满足三选一并就地标记：

```rust
static X: HashSet<i64> = ...; // bounded: 上限 5000，超出丢最小 id
let y = new Map();            // bounded-by-lifecycle: 组件卸载时 clear
let z = new Map();            // bounded-by-data: 键取自六档优先级枚举
```

`audit-unbounded.mjs` 检查命中点 ±3 行内是否有标记，缺失即拦停；例外只能进
`baselines.json` 的 `knownUnbounded` 登记表，**登记只许降不许升**（棘轮）。
`sql-fetch-all`（无 `LIMIT` 的 `fetch_all`）当前是提示级：存量 19 个文件尚未逐个复核，
A6 落地后连同复核结论一起翻正为拦停。

现状：拦停违例 0 组，登记 5 组（`dir_cache` 与两份 `NOTIFIED_REMINDERS` 由 A7 在 Wave 3 清零；
`reminderToastIds` 待复核 `onDismiss` 清理；`activity-format.ts` 属并发会话未提交文件，
留待其会话自行补标记）。

  1 次 canonical 哈希，其余 63 桶零计算（`skipped_chunks` 计数可见）；
  另每表一次 `SELECT uuid, updated_at WHERE is_deleted = 0` 的轻量列扫描（不物化整行）。
  **水位线 = `SyncState.last_pushed_clock_ms`**（push 成功时推进到 push 开始时的时钟快照），
  与 pull 侧冲突判据 `last_synced_clock_ms` **刻意分离**——后者在 pull 结束推进到本轮结束时刻，
  复用它会把「本轮开始前的本地编辑」判成非脏而漏传。
  判据是「时间戳（updated_at > 水位线）∪ 行数（≠ 远端 ChunkRef.count）」的并集：
  单靠时间戳会漏掉 merge 应用远端墓碑造成的本地软删（行时间戳锚定墓碑的 deleted_at，
  可能早于水位线），行数比对正是补这个盲区（用例 `tombstone_applied_row_triggers_bucket_recompute`）。
  A10 依赖的「指纹相等 → 零上传」归因基线未被污染：指纹口径（排除 updated_at/id）未动，
  桶内容语义未动（`bucket_is_unchanged` 只决定「是否重算」，重算结果仍与远端 fp 逐字比对）。
