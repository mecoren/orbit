## 四、数据库打开流程（Tauri 壳）

```
前端启动 → master_auth_has()
 ├─ false → db_init_plaintext(app)            # 免密模式：明文库直接 init_pool_unencrypted
 └─ true  → 解锁页 → master_auth_unlock(pw)
              → derived_key = PBKDF2-HMAC-SHA256(pw, salt, 600_000)
              → 解密 master_auth.json 中 encrypted_db_key → 32B DB Key → hex 化(64 字符)
              → db_init_encrypted(db_key_hex):
                  SqliteConnectOptions(WAL · busy_timeout 5s · max_conn 10)
                  PRAGMA key = x'<hex>'       # SQLCipher 解锁
                  PRAGMA foreign_keys = ON
                  sqlx::migrate!("./migrations").run(&pool)
              → manage(AppState{pool}) → 启动 EVENT_BUS → emit("db-change") 转发任务
```

master_auth.json 格式 v2：`verify_hash = SHA-256(derived_key)`（v1 存 raw derived_key，首次解锁自动升级）。

## 七、双层密钥体系

```
【第一层：本地库加密】
主密码 ──PBKDF2-HMAC-SHA256(salt16, 600k)──► derived_key(32B)
           └─ 包裹随机 DB_Key(32B) ──► master_auth.json { encrypted_db_key, verify_hash=SHA256(derived_key), v2 }

【第二层：云同步 E2E】
同步密码 ──v2 确定性派生──► master_key/data_key（同密码跨设备同 Key）
data_key(32B) ──AES-256-GCM(master_key, nonce12)──► encrypted_data_key（v2 语义为"验证子"）
持久化 sync_crypto_meta.json（全 Base64）：{ salt, encrypted_data_key, data_key_nonce, iterations, key_derivation }
```

规则：

- v2 确定性派生下「密码对 = Key 对」，结构性消灭"密码正确但 Key 不匹配"的分叉态；
  改密即换 Key，必须配合 rekey 全量重传（命令层编排，失败回滚本机密码）。
- 迭代次数 600k 单调不降级；meta 文件损坏 → 隔离为 `*.corrupt-{ts}` 并报错，**绝不返回 Ok(None)**。
  下限校验落点（第五轮 F33）：所有**不可信来源**的 iterations 统一过
  `crypto::ensure_kdf_strength`（下限 = 历史最小值 200k，不取 600k，否则存量 200k
  云端 meta 直接导不进来）——云端 `crypto/config` 导入、本地 meta 解锁、备份文件头三处入口；
  降级值一律拒绝派生（AGENTS.md「PBKDF2 600k 单调不降级」的实现处）。
- 跨设备 Key 分发：上传/下载 `{base_path}/crypto/config`（明文 SyncCryptoMeta JSON）；
  导入带守卫（本地 meta 不一致且未 force → LocalMetaExists）。
- 备份链路（§九）与同步链路共用同一 PBKDF2 迭代常量（单一来源，防强度漂移）。

## 八、云同步管线（cloud_sync）

### 云端布局

```text
{base_path}/
├─ crypto/config                              # SyncCryptoMeta（明文 JSON，跨设备分发 Data Key）
├─ manifest.orsync                            # 唯一真相源（加密）：epoch + 表分桶索引 + 墓碑水位线
├─ manifest.prev.orsync                       # 上一版清单（回滚点辅助，尽力保留）
├─ tables/{table}/{bucket:02}.orsync          # 表级数据分桶（加密，约数十字节 KB/桶）
├─ tombstones/{table}/{YYYY-MM}.orsync        # 墓碑分桶（加密，按本地时区月份）
└─ assets/{hash}.orsync                       # 附件内容寻址（≥8MiB 走分片/续传通道）
```

### 分桶规则（差量成立的前提）

- 桶数固定 `TABLE_BUCKET_COUNT = 64`；`bucket = sha256(uuid) 前 4 字节 BE % 64`。
- **为什么不是顺序切片**：顺序切片（前 N 行一片、再 N 行一片）在中间增删一行后边界整体漂移，
  分片指纹几乎全部变化，差量退化为全量重传。稳定哈希分桶让行的归属只取决于自身 uuid——
  单行编辑只影响它所在的那一个桶。
- 桶内按 uuid 升序序列化；桶指纹沿用 canonical JSON + sha256（排除 `updated_at` / `id`），
  因此「仅时间戳变化」不触发对象重传。
- 桶载荷自描述：`{ table, bucket, items }`；读侧校验 `table` 落在白名单内且与路径一致
  （防篡改与版本不兼容）。

### 清单结构（Manifest）

```jsonc
{
  "layout_version": 1,
  "epoch": 7,                    // 乐观并发版本号：每次成功写入 +1，写入前须匹配
  "device_id": "…",              // 最后写入设备（诊断用，不参与裁决）
  "updated_at": 1758…,
  "tables":     { "todo_tasks": { "chunks": { "3": { "fp": "…", "count": 12, "size": 4096 } } } },
  "tombstones": { "todo_tasks": { "buckets": { "2026-09": { "fp": "…", "count": 3, "max_deleted_at": 1758… } } } },
  "devices":    { "dev-1": { "last_synced_at": 1758… } }
}
```

### Push（差量上传 + 清单 CAS）

1. 读远端清单（`download_with_token`：内容 + 并发令牌 ETag）；404 → 空清单
2. **空数据覆盖守卫**：远端有数据 + 本地全空 + 本机曾同步过 → 阻断（删库重装残留账本场景）
3. 逐表：加载未删行 → 分桶 → 与清单桶指纹比对 → **仅上传变化桶**；墓碑分桶同口径
4. 组装新清单：**远端清单拷贝 + 本地有数据的桶覆盖**。远端有、本地无的桶条目**原样保留**
   （删除语义始终由墓碑表达）→ `epoch + 1` → 登记本机检查点 → 墓碑水位线剔除过期分桶
5. 条件写清单（`If-Match: <etag>`；首次 `If-None-Match: *`）→ 412 或**写后回读校验**发现他端
   写入 → 重新读取后重算重试（上限 3 次），`cas_conflicts` 计数透传
6. 清单落定**之后**才删除过期墓碑对象（顺序不可颠倒，否则他端读清单时 404）

### Pull（清单驱动差量下载）

1. 读清单；不存在 → 云端无数据，直接返回
2. `epoch` 与本地账本一致 → 跳过（零分桶流量）
3. 表集合 = 有数据分桶的表 ∪ 有墓碑分桶的表（数据被删光的表只剩墓碑，漏掉会丢删除传播）
4. 逐表：桶指纹与本地账本快照比对 → **仅下载变化桶**（含墓碑分桶）→ 单表事务内完成
   「数据合并 + 墓碑应用」（原子，无半合并窗口）
5. 用清单刷新本地账本（epoch + 桶索引快照）；失败表回滚其快照，强制下轮重试

### 本地账本（sync_state.json）

```jsonc
{
  "last_synced_at": 1758…,
  "device_id": "…",
  "manifest_epoch": 7,                                     // pull 快速跳过判据
  "remote_tables":     { "todo_tasks": { "3": "<指纹>" } }, // 上次所见远端数据桶指纹
  "remote_tombstones": { "todo_tasks": { "2026-09": "<指纹>" } }
}
```

纯缓存：丢失只损失一次增量能力（退化为完整比对/下载），业务数据不受影响。
**Push 的差量基准始终是实时读取的远端清单**，不依赖本地快照，因此账本漂移不会导致误覆盖云端。

### 冲突合并（LWW，两端确定性收敛）

- 远端有、本地无（按 uuid）→ INSERT（保留远端原始字段；INSERT 分批 50 条）
- 本地有、远端无 → 保留（多设备新增不丢；删除由墓碑表达而非"缺失"）
- 两端都有 → `updated_at` 大者胜；同毫秒平局 `version` 大者胜
- 本地为墓碑 → **复活裁决**：远端存活的 `updated_at ≥` 本地删除时间才复活（走 UPDATE，绝不 INSERT）
- 墓碑应用：`deleted_at ≥` 本地 `updated_at` 才删除（编辑晚于删除则编辑胜出），
  且墓碑的原始删除时间全程不漂移（绑定墓碑自身时间戳，不写同步时刻）
- 冲突裁决计数：`MergeResult.conflicts → PullResult → SyncResult → sync_history` 落库可观测
- **裁决键是逻辑时钟而非裸墙上时钟**（`crates/orbit-core/src/db/clock.rs`）：
  - **推进**：业务写路径的时间戳一律 `ts = max(wall_ms, last + 1)`——同设备内严格单调，
    同毫秒多次写入不再平局，墙上时钟回拨也不会倒退；
  - **接收**：合并时对每条远端 `updated_at` 与墓碑 `deleted_at` 做 `last = max(last, 远端值)`，
    此后本地写入必大于「已见过的最大值」，设备间时钟漂移造成的**系统性** LWW 偏置在首次
    同步后即被消除（慢表重启后靠 `cfg_kv` 持久化恢复，不会回落到墙上时钟）；
  - **折叠而非新增 hlc 列**：`updated_at` 本身就是 LWW 比较键，另起一列会让两把键并存且要
    连带改 11 张表 DDL + 全部写路径 + 双端 DTO 镜像 + FRB 链路；折叠后值域完全等价、向后
    兼容（旧行照常参与比较）、零 schema 变更（决策见 §八 遗留项兑现记录）；
  - `db_loader::now_ms` 保持**纯墙上时钟**语义（`last_synced_at` 设备检查点 → 墓碑回收水位线），
    与逻辑时钟分工不混用。
- **冲突败方副本**（`sync_conflicts` 本地表）：LWW 丢掉的败方整行快照留档 + 设置页查看/恢复 UI。
  - 判据只记**真并发**：本地记录与远端记录都晚于「上次同步成功时的逻辑时钟」
    （`SyncState.last_synced_clock_ms`）；他端顺延更新（本地自上次同步后没动过）不留档，
    避免把每次跨端同步都灌成噪声；从未同步过（基线 0）不留档；
  - 留档与合并**同一事务**（原子）；表容量上限 500 条（超出丢最旧）；
  - 恢复 = 拿败方内容发起一次新的本地写入（新逻辑时钟 + `version + 1`），因此恢复后的
    版本会赢得下一轮同步；只还原内容字段，不还原生命周期（`is_deleted`/`deleted_at`/`created_at`
    保持原行现状）；
  - 本表为**纯本地表**：不进 `SYNCABLE_TABLES`、不进备份白名单（各端各自记录各自的裁决
    现场，跨端混看无意义），口径同 `notification_log` / `todo_activity_log`。

### 引擎与调度

`SyncEngine`（tokio Mutex 互斥，忙时返回 skipped）：

| 入口 | 语义 |
|---|---|
| `sync_now` | 完整同步（pull → push → 附件） |
| `push_only` | 修改后立即推送（不拉取） |
| `pull_then_push` | 启动场景先拉后推 |
| `force_sync` | **进入/退出应用强制同步**（忽略开关，见下） |
| `rekey_cloud_reencrypt` | 以本机为准全量重加密覆盖（改密/迁移/恢复共用） |

错误分类重试：网络 2/4/8s 指数退避、限流 30/60/120s 长退避、认证首错即返。
定时调度器 60s tick（`is_auto_sync && 距上次 ≥ interval`，账本持久化读 DB `last_synced_at`）；
修改后 5s 防抖 `push_only`。

**进入 / 退出应用强制同步**：只要求「存在同步配置 + 已解锁」，忽略 `is_auto_sync` /
`interval_minutes` / `sync_on_change`——「进入应用」「退出应用」本身就是触发条件。

- 桌面进入：延迟 1.5s 触发（避开首屏查询高峰），引擎忙时最多等 3s
- 桌面退出：托盘退出与系统真退出路径**阻塞**执行（进程退出后协程会被销毁，
  不阻塞等于不执行），上限 15s，超时放行并留日志；前端显示退出遮罩
- 移动：`resumed` 触发进入同步、`paused` 尽力同步（6s 超时；被系统冻结则放弃，不承诺可靠）
- 普通关窗是「驻留」而非退出，不触发退出同步

### 墓碑回收（gc）

- 水位线 = 所有登记设备同步检查点的**最小值**；设备数 < 2 时返回 0（不回收，保守）
- 早于水位线所在月份的墓碑分桶：先从清单剔除（随新清单 CAS 上传），清单落定后再删除对象
- 未回收的墓碑保证新设备加入时仍能正确判断删除，不冒复活风险

## 九、全量备份包 .orfullsync 格式

36 字节头 + AES-256-GCM 密文；载荷为 ZIP（`manifest.json` + `business/<table>.json` +
`system/schema_version.json`）整体加密。PBKDF2 迭代次数与同步链路**共用同一常量**
（当前 600k，单一来源）；读侧按容器头内 `iterations` 解密，旧包（200k）仍兼容。

| 偏移 | 长度 | 字段 |
|---|---|---|
| 0 | 4 | magic `"OFS1"`（遗留 `"WFS1"` 读侧兼容） |
| 4 | 16 | salt（PBKDF2，每次备份随机生成） |
| 20 | 12 | nonce |
| 32 | 4 | iterations（BE u32） |
| 36 | 变长 | ciphertext（含末尾 16B GCM tag） |

文件名 `backup{yyyy-MM-dd}-{设备码}.orfullsync`（设备码安全化含 URL 危险字符）；
导入按备份导入白名单整体替换。备份与增量同步是两条独立链路（格式、KDF、路径均不同）。
