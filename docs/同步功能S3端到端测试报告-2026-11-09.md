## 八、问题与建议

1. **移动端每次重启都要重新解锁同步密码**（不缓存 Data Key）。这是既定安全语义，但大库场景下「改一行 → 重启后同步」需重复输密码；若后续做后台同步，需要明确前台解锁作为门控。
2. **移动端大库全量同步耗时显著高于桌面核**：214k 行 / 258 附件在模拟器上 94–205 s（桌面核 38–53 s）。瓶颈在 SQLite 单线程写入与模拟器 I/O，建议后续在移动端补一条 profile 基线（10k/50k 档）避免真机换机恢复体验劣化。
3. **`sync_history` 的 `pulled_count/pushed_count` 是「模块 + 附件」计数**（全量轮 259 = 258 附件 + 1 模块），不是行数；UI 文案已写「拉取 N」，容易读成行数。建议在同步历史里区分「行变更数 / 附件数」。
4. **`sync_state.json` 与业务库必须同生共死**：本轮刻意验证了「只删库不删账本 → pull 整轮跳过」和「删账本 → 全量 pull」两种路径，前者会导致空库拉回 0 条，测试手册已列为必删项，建议产品在「清空数据」入口自动一并删除，避免用户自助清库后误判「云端没数据」。
5. **真机 GUI 自动化可用性**：`adb shell input tap` 在模拟器上首次点击偶发不生效（需重试 1–2 次），本轮所有关键步骤都以 `uiautomator dump` 的 bounds 复核后再点击，未出现误操作导致的数据污染。

## 九、测试范围与限制

1. 阶段 3 的 3.1–3.9 与阶段 4 六项判据**全部在真实壳上完成**：两台模拟器（Flutter + FRB）与桌面（Tauri + React）各自持有自己的库、账本与附件目录，经 S3 真实 HTTP 往返，数据为 215,409 行真实种子 + 258 个真实附件。
2. 阶段 5 使用核心测试台三实例（同一份 `orbit-core` 生产 `pull_then_push` 与真实 OSS HTTP），独立隔离前缀；单元级结论与真机轮互补，未在真机上重做并发编辑（真机改标题需逐点按，无法保证「离线并发」的毫秒级间隔）。
3. 附件「>8 MiB 可打开」的判定为：三端附件目录中该文件存在、字节数 8,912,896、sha256 与源端一致（可完整读取）；未在移动端用播放器/阅读器做二次人工打开。
4. 未做全量 JSON 跨桥 diff（4 万行会顶到桥与内存上限），改用「全表规范化摘要 + 抽样」。
5. 云端对象全部保留，未调用 `cloud_orphan_chunks_gc` / `cloud_unused_attachments_delete`，未调用 `cloud_sync_rekey`。
